## 0 与旧计划的关系

旧版 `地毯式排查升级计划.md`（0.26.0，2026-08-13）已闭环 44 款游戏，
其 F1~F31 修复与「第十轮」流程是地基，全部继承。本计划是**全面升级版**，
解决旧计划的核心缺陷——旧流程中分析者（我）只看工具产出（翻译/跳过/
审核报告），从未独立枚举游戏的全部文本载体；识别率分母由识别链自产自销，
漏洞不可见。本轮升级把「我」变成每个游戏的第一侦查员与对照者。

## 1 全面升级目标

1. **全流程完整记录**：每个游戏从识别到写回，每条文本都有详细记录；
   重译文本保留两次记录（首次 + 重译，两版译文与原因都在）。
2. **我全程参与（上游/中游/下游）**：像培养徒弟一样真实进入每个环节，
   不只是看报告——亲自枚举文件、解包、搜文本、对照、审查、裁决。
3. **识别彻底**：逆向识别全来。我独立找出游戏里所有文本载体与文本，
   与工具识别结果**一一对照**；工具漏了 → 修复补漏 → 排查同类（相似
   扩展名/同形态/同引擎变体）→ 机制升级，确保同类不再漏。
4. **翻译/审校审查**：每条失败与审核不合格逐条裁决，翻译质量不是
   高分的快照而是人工抽审过的结论；审校环节是否真在起作用可验证。
5. **写回审查**：每条写回有记录（成功/失败/问题/验证），确保写回
   正确、不破坏游戏（免实机，靠结构级验证 + 重开验证 + 原子提交）。
6. **工具实质性升级**：通过大量真实游戏闭环，沉淀 F3x 系列修复与
   知识库，每轮闭环都让工具更强。
7. **允许查资料、下载工具**：只要方便识别、提升能力（如新解包器、
   Unity 版本对应关系资料）都可以用。

## 2 记录体系（2026-08-22 全面升级适配）

`docs/all record/<游戏>/` 结构（自动导出由 `hanhua/core/record_writer.py`
单一实现——GUI 手动汉化与 runner 闭环共享同一导出代码，字段完全一致）：

```
summary.md               # 排查总结：统计/发现/修复/闭环状态 + 运行记录
                         #   （请求/Token/耗时/吞吐）+ 哨兵告警 + 经验记忆摘要
recon/                   # ★ 我的侦查记录（本轮核心）
  file-inventory.md      #   全量文件清单：每个非媒体文件的行（路径/大小/形态猜测/结论）
  carriers.md            #   文本载体登记表：文件→容器类型→提取方式→工具是否覆盖
  manual-text.md         #   我人工搜出的文本（含未被工具识别的，标注 discrepancy）
  gaps.md                #   对照差集：工具缺 vs 我找到的，逐条归因（已解释/未解释）
text/
  translated.txt         # 成功文本（逐条全字段，见下）
  failed.txt             # 失败文本（含失败详情）
  skipped.txt            # 跳过文本（含跳过原因分布——哑信号可见化）
  blocked.txt            # 阻断文本：语义审核重译未收敛（坏译文/审核理由/轮次）
  retranslated.txt       # ★ 重译档案：原文/首译（被否）/重译终译/重译原因/轮次/
                         #   处置/审核（收敛后自动从 rejected_candidate 对照留存）
review/                  # 审核记录：review-report.md + 不合格清单逐条裁决
writeback/writeback.txt  # 写回逐文件记录：文件/成功失败/详情/验证结果
analysis/analysis-final.md
fix record/fix-record.md # 失败条目明细 + 分类统计 + 本游戏触发的修复（F 编号）
final report/final-report.md
memory-report.md         # 经验记忆（AgentMemory）报告
```

**每条文本记录字段**（四类 text/*.txt 统一，与记录模板规范 §1A 一致）：

```
来源 | 键位 | 对象（Unity 结构定位） | 原文 | 译文 | 置信度 | 原因 | 角色 |
质量评分（质量门原因全列 + passed） | 翻译评价（审核实质输出） | 需要优化 |
写回（链路视角） | 处置（闭环视角终态） | 审核（审校终态 + 风险）
```

- **质量门原因是核心**：quality_reasons 逐条全列，不得省略/截断。
- **处置行**：每条一目了然——已发布 / 未发布（写回被拒/回显）/
  待处置（阻断/失败/审核待定/审核不合格）。
- **blocked 全字段**：重译前坏译文（rejected_candidate）、审核理由/
  建议、重译轮次、原始输出、失败分类、尝试次数。
- **重译两次记录**：首译存于 blocked/rejected_candidate 或
  retranslated.txt 首译（被否）行，两版译文与重译原因都在。
- **不重复原则**：聚合统计归 summary.md，逐条明细归 text/，分析结论
  归 analysis/——同一信息不出现在两个文件。
- **哨兵告警**：跳过率/回显豁免/单一跳过原因/失败率/语言源保留/
  预算耗尽/记忆拒绝率/dense 形态跳过异常比例自动落盘 summary.md
  （阈值见记录模板规范 §1A），有告警必须在 analysis 中给出处置。

runner（`scripts/all_record_runner.py`）文本导出已委托 record_writer，
仅保留其富写回记录（`_export_writeback_record`：逐栈闸门/逻辑审计/
raw_expansions/writeback_case_rules）与流程编排。

## 3 每游戏闭环流程（11 步，我在每步都真实参与）

### 第 1 步 侦查（我的独立工作，先于工具）
- 枚举游戏目录全部文件（排除媒体：图/音/字/视），每个文件登记：
  路径、大小、头字节（魔数）、Unity 版本痕迹（globalgamemanagers/
  boot.config/global-metadata.dat/程序集版本）、形态猜测。
- 识别容器类型：Unity AssetBundle/SerializedFile、.pak、zip/gzip、
  sqlite、TextAsset（.txt/.json/.bytes）、Mono DLL（#US 堆）、
  IL2CPP（global-metadata.dat）、松散文本文件、自定义容器。
- 可疑形态（未知魔数/伪装扩展名/加密特征）专门记录，必要时下载/使用
  解包工具（UnityPy、AssetStudio、il2cppdumper、dnfile、7z 等）。
- 产出 `recon/file-inventory.md` + `recon/carriers.md`。

### 第 2 步 独立文本清册（我的对照基准）
- 跑 `census`（字节级全量扫描，与提取管线解耦）→ 清册 hits。
- 我从清册里人工抽审 + 对 carriers 里每个载体人工确证（解包看内容）。
- 产出 `recon/manual-text.md`：我确认的文本载体与代表样本。

### 第 3 步 工具识别
- 跑 `scripts/_recognition_report.py <游戏>` 得到：提取池、形态统计、
  skipped 率、缺口清单、证明链分母、待登记类队列、告警。
- 这既是工具识别结果，也是对照对象。

### 第 4 步 一一对照（本轮核心）
- 对照 1（载体级）：我的 carriers 载体表 vs 工具 `find_asset_files`/
  `find_dll_files` 覆盖集合。工具没读的载体 → 盲区。
- 对照 2（文本级）：census 清册 vs 提取池差集（缺口清单）。未解释
  缺口逐条人工裁决：真文本 → 修识别；非文本 → 归因关闭。
- 对照 3（同类排查）：任何发现的漏识别，列出"同类"（同扩展名/同
  容器/同形态/同引擎变体），全部验证一遍，确认无一漏网。
- 产出 `recon/gaps.md`。

### 第 5 步 识别修复（发现即修，同类即查）
- 缺口确认后：修提取器/规则/形态注册表/类注册表，加回归测试，
  全量测试通过后，**同类批量验证**，再重扫本游戏确认补上。
- F 编号继续（F32 起）。修复记录入 `fix record/`。

### 第 6 步 翻译
- 跑 runner 翻译（或已有项目库则增量）。翻译后逐条核对：
  failed 清单每条裁决（真实拦截 vs 误杀）；
  抽样抽审 translated（每游戏 ≥ 3% 或 ≥ 30 条，含长文本/专名/多行）。

### 第 7 步 质量门与语义审核审查
- 审核报告逐条裁决不合格清单；验证审校是否真在工作（判定数与
  风险分流调用率）；术语沉淀逐条审查（防污染，F22/F23 教训）。
- 判定误杀 → 修规则；真实问题 → 反馈重译（重译自动落
  retranslated.txt——首译被否/重译终译/重译原因/轮次全字段；
  未收敛条目落 blocked.txt——坏译文 rejected_candidate 留存）。

### 第 8 步 写回审查
- 写回逐文件记录核对：成功/失败/警告逐条；闸门 PASS/WARN 原因；
  字体验证证据；结构级验证（重开验证/原子提交）。
- 不实机测试（用户指令），但每条失败/警告必须有归因，且确认不会
  破坏游戏（原文件备份/回退路径、staging 机制）。

### 第 9 步 分析 + 记录
- analysis/analysis-final.md：识别缺口统计、失败分布、修复清单、
  观察项；summary.md 哨兵告警逐条有处置。
- summary.md 汇总（含运行记录：请求/Token/耗时/吞吐）；fix record/
  完整修复过程。

### 第 10 步 知识库沉淀
- 新形态/新载体 → Unity 结构库；新失败 → fail_case 库；术语/词对
  污染 → 退休/清洗；审核沉淀 → 语境保护。

### 第 11 步 闭环清理
- 项目库清理（保留原版游戏，删 `<游戏>_汉化` 残留）；final report
  落盘；更新本计划进度表；继续下一个游戏。

## 4 执行规则

- **顺序**：D:\游戏 字母序，排除已闭环（44）+ 自带中文（electric-
  trains）+ 杂目录（_ 开头/scan/copy/tmp 后缀）。队列见下。
- **不停**：每游戏闭环后立即接下一个；翻译/审核耗时期间并行做侦查、
  审查、修复、测试。
- **修复原则**：宁漏勿坏（写回侧）；识别侧宁严勿漏（多识别少跳过）；
  跳过是哑信号——每个 skipped 高占比形态必须有解释。
- **模型**：沿用四模型本地推理（翻译 1.8B/审核 4B/reranker/embedding），
  服务复用 EXTERNAL 模式。
- **免实测免云端**：写回验证靠结构级证据 + 重开验证 + 原子提交，
  不做实机启动、不用云端审核。
