# 翻译质量保障架构连接审计与解决方案

日期：2026-08-13  
审计对象：`docs/翻译质量保障系统实施计划.md`、提交 `4648430`、2026-08-13 当前未提交工作树  
审计方式：计划承诺矩阵、生产调用链追踪、状态与持久化追踪、GUI/headless 对照、测试证据反查  
范围：只审计和提出方案，不修改实现

## 1. 结论

昨晚的更新完成了大量有价值的 **Module**，但还没有形成计划要求的「检索 → 翻译 → 检查 → 筛选 → 深审 → 修正 → 记忆」闭环。

目前更准确的描述是：

> 硬规则翻译链已经成熟；四级审核、语境库、Reranker、Embedding、四模型运行时分别具备实现和单元测试，但生产入口缺少统一装配、审核状态机缺少发布事务，导致部分能力只存在于 Module 内，或者只在测试中工作。

最严重的结果不是“效果没有最大化”，而是：

1. 4B 审核可判定 MAJOR/CRITICAL，但坏译仍可能被写回游戏。
2. 坏译在深审前已进入 ProjectStore memory 和 AgentMemory，审核门禁来不及生效。
3. GUI 和 headless 都未启用反馈重译、再审和审核后的记忆撤销。
4. ContextStore、VectorRecall、RerankGate 没有接入两个生产入口，当前运行价值接近零。
5. 模型启动、鉴权、取消、端口、资源释放各自实现，策略已经出现明显漂移。

因此，下一步不应继续增加规则或新 Module。应先建立一个深的 `LocalizationPipeline` Module，把已有能力收拢到唯一 Interface 后面，让 GUI、headless 和测试跨同一个 Seam。

## 2. 证据等级

- **已证实**：静态调用链能明确证明参数未传、分支不可达或发布门未检查。
- **高概率风险**：实现已经存在缺陷，但实际影响量需要真实项目统计。
- **待量化**：计划给出百分比目标，仓库尚无足够评估集或生产指标证明达标。

本文的问题均至少有静态代码证据；不会把“有类、有测试”视为生产能力已经生效。

## 4. 当前真实调用链

### 4.1 GUI

```text
TranslatePage
  → 构造 BatchTranslator
     ✓ ProjectStore
     ✓ Glossary / Knowledge pairs
     ✓ AgentMemory
     ✗ ContextStore
     ✗ VectorRecall
     ✗ RerankGate
  → translator.run
     → 机械质量门通过
     → 立即写 ProjectStore memory
     → 立即向 AgentMemory 提案并 flush
  → review_entries
     ✓ entries / glossary / max_send_rate
     ✗ translator
     ✗ memory
     ✗ app_dir/resource root
     ✗ cancellation token
  → 只持久化 flagged 的 issue/reason/suggestion
  → writer 只检查 quality_passed/confidence
```

### 4.2 Headless runner

```text
all_record_runner
  → 构造 BatchTranslator
     ✓ ProjectStore / Glossary / Knowledge / AgentMemory
     ✗ ContextStore / VectorRecall / RerankGate
  → translator.run
     → 提前写两层记忆
  → review_entries(entries, glossary)
     ✗ translator / memory / app_dir / cancellation / settings strategy
  → 写 review-report
  → project.write_all
```

### 4.3 最关键的反差

`BatchTranslator` 的 Interface 已经允许 `context_store` 和 `vector_recall`，`review_entries` 的 Interface 也允许 `translator` 和 `memory`。问题不在 Module 缺失，而在两个 Composition Root 没有装配这些 Adapter。测试多在 Module 内注入 fake，因此证明了实现“可以工作”，没有证明应用“正在使用”。

## 5. P0：会破坏质量承诺或发布安全的问题

### P0-1 深审结论不参与写回门禁

**证据**

- `hanhua/core/reviewer.py:523-532`：只有 `translator is not None` 才执行反馈重译。
- `hanhua/ui/pages/translate_page.py:596-600`：GUI 未传 translator、memory、app_dir。
- `scripts/all_record_runner.py:544-546`：runner 同样只传 entries/glossary。
- `hanhua/core/quality.py:1125-1142`：`is_write_ready` 只检查 status、translation、`quality_passed`、confidence。
- `hanhua/core/writer.py:77-83` 及 Unity writer：不检查 `review_level`、`review_blocked`、`need_revision`、`need_retranslate`。

**影响**

机械质量门通过、语义审核判 MAJOR/CRITICAL 的译文仍保持 `translated + quality_passed=True`，可以进入写回。审核目前更多是报告能力，而不是发布门。

**解决方案**

建立 `ReviewOutcome → Persistence → WriteGate` Seam：

- 新增显式终态：`APPROVED`、`APPROVED_MINOR`、`NEEDS_REVISION`、`BLOCKED`、`REVIEW_ERROR`、`CANCELLED`。
- `is_write_ready` 只接受 approved 终态；同时保留机械质量门作为第一道防线。
- MAJOR/CRITICAL 不能继续保持 publishable 状态。
- blocked 时保存 `rejected_candidate` 和审核理由，发布译文清空或回退原文，`quality_passed=False`。
- 数据库更新必须原子写入 translation、status、quality、review outcome 和 attempt trace。

### P0-2 反馈重译、再审和记忆门禁在生产入口未启用

**证据**

- `review_entries` 有 translator/memory 参数，但 GUI/runner 均未传。
- GUI 只持久化 flagged 的 `review_issue/reason/suggestion`，没有持久化完整 `review_level/blocked/need_*`。
- reviewer 对 entry 的修改停留在内存，生产入口没有统一 `batch_update_translation_results`。

**影响**

计划 T1-4、T1-5、T1-6 在真实运行中没有形成闭环。

**解决方案**

不要在 GUI 与 runner 分别补几个参数。新增 `LocalizationPipeline.run_review()`，它持有 translator、store、reviewer、cancel token 和有效配置，负责：

1. 风险评估；
2. 审核；
3. 反馈重译；
4. 再审；
5. 决定终态；
6. 原子持久化；
7. 记忆提交或撤销；
8. 发布资格更新。

GUI/headless 只订阅进度事件，不再拼接审核业务。

### P0-3 坏译在深审前污染两层记忆

**证据**

- `hanhua/core/batch_translator.py:775-785`、`:856-867`：机械质量门通过后立即写 ProjectStore memory，并向 AgentMemory `propose_deferred`，随后 flush。
- 深审在 `translator.run()` 完成后才发生。
- 真实入口未把 memory 传给 reviewer，无法撤销。

**影响**

4B 后续判为 CRITICAL 的错译可能已经成为下一轮精确命中或跨游戏参考。系统越运行，错误可能越稳定。

**解决方案**

把记忆改成审后提交：

```text
mechanical_pass
  → PendingEvidence（只属于 run_id）
  → review approved
      → commit ProjectMemory
      → propose AgentMemory
      → enqueue vector/context evidence
  → rejected/blocked/error
      → revoke existing ProjectMemory
      → reject/retire AgentMemory evidence
      → 保存错误案例
```

若为了性能必须提前写库，也只能写 `pending_review` 桶，所有查询 Adapter 默认排除该状态。

### P0-4 risk_gate 的 quality_failed 信号不可达

**证据**

- `risk_gate.py:122-124` 对 `status == failed` 生成强制风险信号。
- `reviewer.py:453-457` 在调用 gate 前只保留 `status == translated` 且 translation 非空的条目。

**影响**

计划要求的“质量门最终失败强制送审”没有真实调用路径。测试甚至把 failed 不送审固化为现状。

**解决方案**

风险输入必须是包含候选与失败证据的 `TranslationCandidate`，而不是只接收 publishable TextEntry。failed 条目如果有 rejected candidate 就送语义诊断；没有候选则直接进入 blocked/error report，不伪装成已审核。

### P0-5 强制风险会被 15% 配额截断并归入 passed

**证据**

- `risk_gate.py:190-196` 对所有 risky 共用比例预算。
- 超出预算的风险条目被追加到 `passed`。

**影响**

大量机械失败或硬冲突出现时，最应该强制处理的条目也可能被“成本控制”放行；统计名称还会把截断误导成通过。

**解决方案**

拆分双通道：

- `mandatory`：机械失败、结构/术语硬冲突、关键功能文本，不受抽样配额；超过系统处理能力时阻断发布并进入人工队列。
- `discretionary`：多义词、长句、角色文本等概率风险，才受 5/15/30% 预算。
- 返回 `deferred_due_to_budget`，永远不要命名为 `passed`。

### P0-6 审核与再审 fail-open

**证据**

- `SemanticReviewer.review_one` 吞掉所有服务与解析异常并返回 None。
- `review_batch` 直接遗漏失败条目，没有 coverage invariant。
- `_parse_level` 对未知或空值倾向默认 PASS。
- `_retranslate_with_feedback` 在 `_re_review` 返回 None 时写 `review_level=PASS` 并宣告收敛。

**影响**

401、超时、模型空输出、JSON 漂移可能被表现为“没有发现问题”或“重译已收敛”。这是安全关键 Seam 上的错误语义。

**解决方案**

- 审核结果必须显式包含 `VERDICT | TRANSPORT_ERROR | PARSE_ERROR | UNAVAILABLE | CANCELLED`。
- 约束 `reviewed + errors + cancelled == sent`。
- 严格模式错误即 BLOCKED；平衡模式进入 NEEDS_HUMAN_REVIEW；任何模式都不得转成 PASS 或沉淀记忆/术语。
- 报告分别统计模型判定失败和业务不合格。

### P0-7 blocked 没有恢复安全状态

**证据**

`reviewer.py:594-608` 每轮先写入新的 candidate；两轮仍 CRITICAL 时只打 `review_blocked=True`，没有清除 candidate、没有改 status，也没有撤销机械 `quality_passed=True`。

**影响**

即使未来把 blocked meta 持久化，当前写回门仍可能写入最后一次语义失败候选。

**解决方案**

BLOCKED 是完整领域状态，不是一个附加布尔字段。进入 BLOCKED 必须原子完成：

- `status=blocked`；
- `quality_passed=False`；
- publishable translation 清空或安全保留原文；
- `rejected_candidate` 单独保存；
- ProjectMemory/AgentMemory 撤销；
- 写回门再次拒绝 blocked。

### P0-8 GUI 审核模型根目录依赖 cwd

**证据**

- reviewer 默认 `app_dir=Path.cwd()`。
- GUI 调 review_entries 未传 `state.app_dir/resource_dir`。
- 翻译模型由 AppState 持有正确资源根。

**影响**

从桌面快捷方式或其他目录启动时，翻译模型可用而审核模型可能去错误的 `models/` 查找；异常又被吞掉，形成静默无审核。

**解决方案**

禁止模型 Module 使用 cwd 作为生产默认值。由唯一 RuntimeCoordinator 注入 `resource_root`、`state_root` 和 manifest。

### P0-9 深审取消链断裂

**证据**

GUI stop 只停止 translation run/local model；review_entries、review_batch、chat 没有 cancellation 参数。单条审核可等待长超时，多条串行时停止按钮无法及时生效。

**解决方案**

取消 token 必须穿过 Pipeline → reviewer → runtime request；每条前后检查，HTTP 使用短读超时/可中断请求。取消是显式终态，不能归入 error 或 pass。

## 6. P1：显著降低架构价值和长期可靠性的问题

### P1-1 ContextStore、VectorRecall、RerankGate 没有生产 Adapter

**证据**

- 全仓生产代码没有 `ContextStore(...)` 构造点。
- `VectorRecall(...)` 只出现在自身 docstring 与测试。
- `RerankGate(...)` 无生产构造或调用。
- GUI/runner 构造 BatchTranslator 时均未传 context_store/vector_recall；BatchTranslator 也没有 rerank Interface。

**影响**

阶段 2–4 的主要能力只在单元测试和冒烟脚本中存在。`vector.db` 没有生产索引写入者。

**解决方案：KnowledgeRetrieval Module**

提供一个深 Interface：

```python
evidence = retrieval.resolve(candidate_context)
# evidence.direct_fill
# evidence.references (Top-K, typed, with provenance/confidence)
# evidence.risk_context
# evidence.degradation
```

Implementation 内部负责：

- ProjectMemory 精确命中；
- AgentMemory；
- Glossary/Knowledge；
- ContextStore；
- VectorStore/Embedding；
- Reranker；
- prompt budget；
- 降级与指标。

GUI/headless 只注入同一个 retrieval Adapter。不要让 BatchTranslator 的 Interface 继续膨胀成十几个可选依赖。

### P1-2 ContextStore 合并相反证据并覆盖来源

同 `(source_text, fingerprint)` 已存在时，`add_entry` 只加 evidence、更新 confidence/game，不比较 `recommended_translation` 和 `correct_meaning`。相反译法会被当作支持证据，game 被最后写入覆盖。

**方案**：拆成 `context_evidence` 与 `context_canonical`。每条证据保留 game、来源、review verdict、translation；共识聚合才更新 canonical；分歧置 suspicious。重复同一游戏不能算独立证据。

### P1-3 多义词风险未消费语境证据

计划要求“多义词且语境库无记录”才送审；当前 risk_gate 对多义词无条件打信号，Interface 也没有 context evidence 参数。可靠的 Resume 语境仍占用有限审核预算。

**方案**：KnowledgeRetrieval 输出 `ContextEvidence` 给 RiskPolicy；只有缺失、冲突或低置信才产生 polysemy risk。

### P1-4 C5 候选、激活、冲突统计语义不可信

`add_reviewed` 对 candidate 与 activated 都返回空串；reviewer 因此统一计入 pairs_added。已存在 term 的不同 translation 会被 UPDATE 覆盖，第二游戏可能把冲突词直接升级 active。

**方案**：返回结构化 `DepositResult(REJECTED|CANDIDATE|ACTIVATED|CONFLICT)`；唯一语义改为 normalized term + sense/context key；只有“至少两个独立游戏、相同译法、兼容语境”才能激活。日志分别报告候选、激活、拒绝和冲突。

### P1-5 从一次失败审核建议直接造术语，证据过弱

当前从 MAJOR/CRITICAL 自由文本 suggestion 正则抽词对并沉淀。这是模型对坏译的一次建议，不是二审 PASS 或人工确认。

**方案**：建议只能创建 proposal；修正版经过二审 PASS 才形成 `review_confirm` 证据，人工修正确认权重最高。记录模型/版本/entry locator/before/after/verdict。

### P1-6 人工修正不回流，旧审核标记可能残留

`set_manual` 只更新 translation/status/机械质量 meta，不撤销坏记忆，不清完整 review 字段，也不写 AgentMemory、ContextStore、Glossary 或向量索引。

**方案**：新增 `ManualCorrection` Interface，原子执行：清旧审核状态、撤销旧证据、写最高权重人工证据、更新 context/term proposal、发出 vector outbox、写审计日志。

### P1-7 审核语义错误没有进入 fail_case 闭环

runner 的 fail_case 主要来自机械 `quality_reasons`；CRITICAL/MAJOR 没有结构化写入 wrong translation、correct translation、error type、review reason。

**方案**：使用强类型 `review_failures` 或版本化 JSON schema；收敛与未收敛均记录，但只有二审 PASS/人工确认译文可作为正确例。KnowledgeRetrieval 可召回相似失败作为反例。

### P1-8 GUI 启动会清空项目 entries/memory

`main.py:22` 调 `clear_all_project_records`；该流程调用 ProjectStore.clear_records，清 files、entries 和 memory。项目级翻译记忆因此无法自然跨应用重启存在。

**方案**：只清 session/runtime 临时状态；项目记录按 run_id/version 隔离，显式“清项目缓存”才删除。pending/blocked 不参与命中。

### P1-9 attempt 预算没有真正与审核轮共享

failure attempt 使用对象级 `_attempt_mark=id(entry)` 幂等，同一个 entry 的多轮反馈重译可能只计一次；反馈重译也未在入口前检查剩余预算。

**方案**：AttemptTrace 使用持久化 `(run_id, phase, round, reason)`；每轮操作独立计数，重试策略集中在 Pipeline，而不是 client、batch、reviewer 多处各自重试。

### P1-10 四模型运行时重复实现导致策略漂移

review/rerank/embed 各复制进程管理。已经发生：

- review probe 带 Authorization，rerank/embed probe 不带；
- registry 声称 rerank/embed fixed CPU，但启动仍 `gpu_layers=-1`；
- release 丢进程引用，AppState.close 只停止翻译模型；
- keep_alive 计划值没有真正落进 llama-server 生命周期；
- review 会按固定端口强杀占用 PID，rerank/embed 又没有同等清场策略；
- 取消/超时路径可能留下进程、日志句柄或 runtime state。

**解决方案：RuntimeCoordinator Module**

唯一 Interface：

```python
with runtime.acquire(kind, effective_config, cancel) as endpoint:
    ...
```

Implementation 统一：manifest 精确路由、硬件计划、actual signature、authenticated probe、端口租约、owned PID、refcount、idle TTL、取消、日志、故障清理、退出政策。fixed_cpu 必须在命令构建处断言 `gpu_layers == 0`。

### P1-11 GUI/headless EffectiveRunConfig 不一致

GUI 尊重 ai_review_enabled 和 fast/balanced/strict；runner 使用 `--no-review` 与默认 15%，不读取相同策略。模型 app_dir 和报告字段也不同。

**方案**：统一 `EffectiveRunConfig`，优先级为 CLI override > settings > defaults；每次运行把完整配置快照、来源、模型 hash、prompt/rule 版本写报告。

### P1-12 模型路由与运行签名不够可复现

registry 按文件名模糊匹配并取排序第一；多量化并存可能静默选错。local_model runtime signature 可能记录原始配置而非实际 planner 结果，外部复用后并发判断也可能与真实进程不一致。

**方案**：manifest 固定 kind → exact path + sha256 + capabilities；runtime state 写 effective plan、模型 hash/mtime、ctx、actual layers、parallel、runtime version，并在 probe 时校验。

## 7. P2：会造成噪声、误导和维护成本的问题

### P2-1 Rerank 降级结果没有可信度语义

服务失败时按原序返回 Top-K 且 probability=0；调用方若只判断非空就可能注入未经评分候选。glossary 候选只传 source 字符串，还丢失 target。

**方案**：统一 typed candidate：source、target、origin、scope、evidence、score、ranked_by。服务失败时执行明确的启发式 ranking 或不注入，不能返回“看起来成功”的列表。

### P2-2 HTTP retry 与业务 attempt 重叠

Client 内部 retry 和 Batch/Review 业务 retry 各自隐藏真实尝试次数，失败预算和报告无法准确解释一次译文经历了几次请求。

**方案**：client 返回 `AttemptTrace`；Pipeline 统一决定业务重试，底层只处理连接级短暂 retry，并把次数暴露出来。

### P2-3 接通检查标准偏弱

现有《模块接通检查记录》把“Module 被某处引用、单元测试通过、模型冒烟成功”视为接通。它没有验证生产 Composition Root、持久化、发布门、第二轮消费和错误降级。

**方案**：以后接通必须满足五项证据：

1. 生产入口构造真实 Adapter；
2. 调用产生可观测指标；
3. 状态落库并可重启恢复；
4. 下游实际消费该状态；
5. 失败时门禁和降级符合策略。

## 8. 推荐目标架构

```text
GUI / Headless / Future CLI
          │
          ▼
LocalizationPipeline  ← EffectiveRunConfig
  ├─ RuntimeCoordinator
  │    └─ translate/review/rerank/embed leases
  ├─ KnowledgeRetrieval
  │    ├─ ProjectMemory
  │    ├─ AgentMemory
  │    ├─ Glossary / Knowledge
  │    ├─ Context evidence/canonical
  │    ├─ Vector index
  │    └─ Reranker
  ├─ TranslationEngine
  ├─ MechanicalQualityGate
  ├─ RiskPolicy
  ├─ SemanticReview
  ├─ ReviewOutcomePersistence
  ├─ EvidencePromotion / Revocation
  └─ PublishGate
          │
          ▼
      Staging + verification
```

### 8.1 LocalizationPipeline 的 Interface

调用者只需知道：输入项目、有效配置、取消 token、事件回调；输出 `RunOutcome`。调用者不应知道先创建哪个数据库、什么时候 flush memory、审核失败是否放行或哪个模型占哪个端口。

这会显著增加 **Depth**：复杂行为被集中在一个 Interface 后面；GUI/headless 获得相同 **Leverage**，维护者获得相同 **Locality**。

### 8.2 KnowledgeRetrieval 的 Interface

负责“当前条目可用的全部证据”，而不是让 BatchTranslator 了解每一种库。新增/替换检索方式只改变 Implementation，不扩张翻译 Interface。

### 8.3 RuntimeCoordinator 的 Interface

四模型各自的进程 Module 目前是浅且重复的。统一后，鉴权、端口、配置签名、CPU/GPU、取消和清理只修一次。

## 9. 状态机建议

```text
PENDING
  → TRANSLATING
  → MECHANICAL_REJECTED ───────────────→ BLOCKED / RETRYABLE
  → MECHANICAL_APPROVED
       → REVIEW_NOT_REQUIRED ──────────→ APPROVED
       → REVIEW_PENDING
            → PASS ────────────────────→ APPROVED
            → MINOR ───────────────────→ APPROVED_MINOR
            → MAJOR/CRITICAL
                 → REVISING
                 → MECHANICAL_RECHECK
                 → SEMANTIC_RECHECK
                      → PASS/MINOR ─────→ APPROVED
                      → ERROR ──────────→ NEEDS_HUMAN_REVIEW
                      → still bad ──────→ BLOCKED

只有 APPROVED / APPROVED_MINOR 可进入 PUBLISHED。
```

`quality_passed`、`review_level`、`review_blocked` 多个松散布尔字段不应共同承担状态机；它们可以作为审计证据，但发布资格必须来自单一终态。

## 12. 可观测性与验收指标

每次运行至少输出：

- 各检索来源候选数、命中数、采用数、拒绝数；
- context/vector/rerank capability 状态与降级原因；
- mandatory/discretionary/deferred 数量；
- sent/reviewed/error/cancelled 覆盖恒等式；
- PASS/MINOR/MAJOR/CRITICAL/blocked 分布；
- 反馈重译轮数与最终收敛率；
- PendingEvidence committed/revoked 数；
- ProjectMemory/AgentMemory/Context/Glossary/Vector promotion 与 conflict 数；
- 最终 publishable、blocked、human-review 数；
- 四模型 effective route、hash、backend、ctx、parallel、启动/复用/卸载；
- 完整 AttemptTrace 和耗时。

计划中的目标只有在这些指标上才算验收：

- CRITICAL 检出率与 MAJOR+CRITICAL 检出率：固定标注集评估，而非模型冒烟。
- 4B 调用率：只约束 discretionary；mandatory 单独统计。
- 重译收敛率：分母只含真正执行过重译且再审有判定的条目。
- Precision@5：固定人工标注集。
- 连续三游戏错误率趋势：必须定义相同口径和版本快照。

## 13. 不推荐的修法

1. 不要只在 TranslatePage 和 runner 各补四个构造参数。这样会继续制造两套流程。
2. 不要只给 `is_write_ready` 加一个布尔判断后宣布闭环完成；持久化和记忆污染仍存在。
3. 不要继续给 review/rerank/embed 分别复制端口、鉴权和进程修补。
4. 不要把更多知识库直接拼进 glossary 强制词对；证据类型和适用范围不同。
5. 不要用更多 Module 单元测试替代生产 Composition Root 契约测试。
6. 不要把审核不可用解释为“保守通过”。真正保守是不可发布或转人工。

## 14. 最优先建议

先做 Phase A：`ReviewOutcome → Atomic Persistence → PublishGate`。

原因：当前系统最危险的不是检索能力没用上，而是已经发现语义错译后仍可能写回，同时坏译会进入记忆。先把发布安全和状态事务修正，再接 Context/Rerank/Vector，新增能力才不会放大污染。

Phase A 完成后，第二优先是 PendingEvidence；第三才是 KnowledgeRetrieval 的生产接线；RuntimeCoordinator 可与第三阶段并行，但必须在全面启用 Rerank/Embedding 前完成，否则四个本地模型会放大端口、显存和孤儿进程问题。

## 15. 最终判断

计划方向是正确的，核心 Module 也不是白做。问题在于当前架构横向扩展了很多能力，却缺少纵向贯穿一次本地化任务的深 Module。结果是每个局部看起来都合理，但端到端的状态、证据、发布和资源所有权没有集中。

完成本文推荐的三项架构深化后：

- `LocalizationPipeline` 提供任务闭环的 Depth；
- `KnowledgeRetrieval` 提供知识与语境的 Depth；
- `RuntimeCoordinator` 提供四模型运行时的 Depth。

届时“检索、翻译、检查、筛选、深审、修正、记忆”才会通过同一条生产调用链彼此强化，而不是停留在“模块都在仓库里”的完成感上。
