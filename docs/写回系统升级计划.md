## 一、实测失败根因链(已确认,非猜测)

**B1(P0)#US `heap_offset` 语义错位 —— MyRustySubmarine 实证根因**

- 提取端(mono_dll.py:511):`heap_offset = heap_file_offset + offset`,其中 `offset` 是
  `_walk_us_heap_records` 返回的 **data_offset(数据区位置,压缩前缀之后)**;
- 写回端(writer.py `_patch_dll`):把 `heap_offset` 当**记录起始(前缀)位置**用:
  `data_start = offset + len(new_prefix)` 又加了一次前缀长度 → 前缀字节覆盖数据区开头、
  新数据与新 flag 整体错位(可覆盖下一条记录/堆外);
- 重开验证 `records.get(offset)` 拿「数据位置」去匹配「前缀位置」字典 → 必然 miss →
  抛「#US 记录缺失 offset=45922」。
- **测试与提取端契约不一致**(测试手写 `heap_offset=4` 当前缀位置,恰好自洽)→ 测试全绿、
  真实失败——同源盲区第 3 例(前两例:IL2CPP explicit pos+4、共享 data_index)。

**B2(P0)#US 重开验证依赖全量流式遍历 —— 残留区免疫缺失**

- 译文短于原文时,新记录变短,新 flag 之后残留旧数据字节;
- 重开验证 `_walk_us_heap_records` 从堆头流式遍历,残留字节被解析成非法前缀
  (`ln<=0` / 前缀解析失败)→ `break` → 残留区之后的记录全部丢失 → 误报「记录缺失」;
- 运行时 CLR 按 token 偏移**单记录定位**读取(自包含,不依赖前后记录),不受影响——
  但我们的验证必须与 CLR 语义一致,不能依赖「堆紧凑」这一假设。

**B3(P0)写回残留旧字节未清零**:新 flag 之后到旧记录末尾的残留字节保留在文件中。
运行时无害,但文件脏:二次扫描/其他工具按流式解析会在残留区断开。

**B4(P1)文件锁定致写回失败 —— 上次 93 游戏审计 7 失败全因**:

- `_atomic_write_bytes` 的 `os.replace` 抛 WinError 5(拒绝访问):游戏进程仍在运行 /
  Windows Defender 扫描窗口 / 杀软隔离;
- 失败后无重试、错误信息未指明「文件被占用」,用户无从处理;
- 7/93 失败:handshakes、lilys-day-off(其余 5 个见 _writeback_log.txt)。

## 五、风险与边界

- 提取端 heap_offset 语义修改会改变已存项目的 meta——旧项目(已有翻译库)里
  存储的 heap_offset 是数据位置,新写回端按前缀位置处理会错位。需**兼容**:
  `_patch_dll` 预检时若 ln 校验失败,尝试按「数据位置-旧前缀宽」解析(向后兼容旧库),
  或版本化 meta(加 `record_offset` 字段,新提取端写新字段,写回端优先用新字段)。
  → 采用**双字段方案**:新提取端写 `record_offset`(前缀位置)+ 保留 `heap_offset`(数据位置);
  写回端优先 `record_offset`,缺省时回退 `heap_offset`(旧库)→ 兼容无迁移成本。
- 残留区清零不改变运行时行为(CLR 单记录定位),只影响文件字节——白名单
  (IL2CPP 差异白名单)在 DLL 侧尚无字节级白名单,残留清零不触发任何拒绝逻辑。
- 鲁棒遍历可能多产出少量垃圾记录(残留区字节被解析成短记录)→ 提取侧字符串级
  过滤(控制字符/无空格标识符)已覆盖,不产生可译条目。
