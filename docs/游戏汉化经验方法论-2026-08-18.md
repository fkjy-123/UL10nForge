## 一、核心教训（按严重度排序）

### 1. TMP 字体跨版本替换是最大的坑（条纹/口口根因）

**现象链**：中文口口口（组件引用无中文字体）→ 替换字体后「一个字里很多小字」
（m_fontInfo 段 4 字节错位 → mono 反序列化后 atlas 尺寸读错 → UV 错乱）。

**根因**：工具生成的 TMP_FontAsset bundle（Unity 2019.1 / TMP 2.1.0）与目标
游戏主文件（Unity 2019.4 / TMP 2.1.1）存在**序列化格式差异**，字节直接
复制进主文件会错位：

| 差异点 | bundle (2.1.0) | 主文件 (2.1.1) |
|---|---|---|
| m_AtlasTextureIndex 位置 | 在 m_AtlasTextures 数组**后** | 在 m_AtlasPopulationMode **后**（数组后也有） |
| 纹理数据 image data len | save_typetree 输出位置 | 主文件固定 @104 头部 |
| m_fontInfo 段 | 92B（无 len 字段） | **96B（len 4 + 23 floats 92）** ← 条纹根因 |

**方法论**：
- **跨版本移植数据必须逐字段验证结构**（字段序列断言），不能只验「数值对」。
- m_fontInfo 段少 4 字节 → 后续所有字段偏移 4 → 引擎读到的 atlas 尺寸是错的
  → UV 计算错 → 每个字形采样错误区域 → 「一字多字/条纹」。**4 字节偏移 = 灾难**。
- 纹理数据不要用 `save_typetree`（UnityPy 模板与主文件布局差 8-9 字节 →
  引擎逐行错位 → 水平条纹）。**以主文件原纹理为模板手工组装**（104B 头部 +
  像素 + 尾部）。
- 字体替换后必须验证：atlas 区域字形（'中' 区域应为「中」）、字段序列。

### 2. 字节级全局替换会误伤非文本对象（黑屏根因之一）

**现象**：引用替换（(fileID=2, pathID=2417)→2409 等）后，31 个 level 的
MeshRenderer/LightmapSettings/Transform/PlayableDirector 被误改
（pathID 恰好匹配）→ 关卡加载崩溃/卡死。

**方法论**：**一切字节级替换必须限定在目标组件/对象内部**（组件级操作），
绝不全局 replace。参考 `hanhua/core/unity/tmp_font.py::retarget_component_refs`。

### 3. rawstr 提取会翻译对象名/逻辑键（过场崩溃根因）

**现象**：写回后过场动画流程空指针崩溃。根因：rawstr 二进制扫描把
MonoBehaviour 的 m_Name（对象标识名）、InputModule 轴名、CutsceneScript
键（"Play"）、Button/逻辑组件字符串当文本提取翻译 → 游戏按原名查找断链。

**方法论**：
- **m_Name（对象标识名）绝不进入翻译池**（typetree 路径已有排除，rawstr
  路径按固定布局 @28 排除——见 `_mono_object_name_span`）。
- 写回后执行**非显示对象保护**（显示脚本白名单外的对象恢复原版——
  见 `hanhua/core/unity/protect.py`）。

### 4. CSV 写回漏行/行号错位（过场对话英文）

**现象**：CutsceneLocalization 写回漏 158 行（ENG 列英文）→ 过场全英文。
以及引号内逗号导致 csv.reader 行合并 → 按行号写回串行。

**方法论**：
- 写回后执行**完整性校验**（源列残留英文检测——`verify_csv_writeback`）。
- **按 ID 列写回**（不依赖行号——`apply_csv_by_id`）。
- 多轮写回时每轮校验，防止「部分写回后文件变化 → 下轮行号错」。

### 5. 二分排查法有遗漏（用户实证）

**现象**：二分「两个中一个有问题 → 归因于它」可能遗漏另一个也有问题。

**方法论**：**列出全部差异对象 → 分类 → 全量修复**，不用二分定位单个根因。
Rendezvous：非显示对象全量还原（650 个）+ 显示文本校验后才稳定。

### 6. 自动化测试必须验证「真正进入目标流程」

**现象**：SendKeys 按键未聚焦游戏窗口 → 假 ALIVE（没进过场）→ 误判。

**方法论**：自动化验证必须检查**流程日志标志**（如 "Load Misc" 出现次数），
确认进入了目标流程，再判断崩溃/存活。

### 7. 工具链完整链路优于手搓 API

**现象**：直接调 llama-server API 翻译不稳定（精简 prompt 回显、无 JSON
输出）。工具链 BatchTranslator（回显检测/重试/占位符校验）稳定。

**方法论**：**翻译一律走工具链**（BatchTranslator + LocalOpenAIClient），
不手搓 API。Hy-MT2 需要工具式长 prompt（角色策略），精简 prompt 触发回显。

## 二、排查方法论（黄金流程）

1. **原版对比**：原版正常 = 汉化引入（最快的方向判定）。
2. **全查不二分**：列出全部差异对象（按类型/脚本/字段分类），全量修复。
3. **崩溃转储分析**：同一崩溃地址 = 同一根因；崩溃 vs 卡死（无转储）不同。
4. **日志矛盾分析**：health 更新但日志停止 → 主线程卡死（协程/Update 停）。
5. **真实流程验证**：验证「真正进入目标流程」的日志标志，再判崩溃/存活。
6. **数据层验证**：逐字段结构断言（跨版本移植）、字节级 diff、atlas 区域检查。

## 四、Rendezvous 案例速查

- 游戏：Unity 2019.4.22f1 + TMP 2.1.1 + Mono + UGUI/TMP 混合
- 语言：CSV 词典（TextAsset#30-38，13 列，ENG 源列覆盖写回）
- 字体：游戏自带 7 个 TMP_FontAsset（Coda/arial/NotoSC 等）；
  NotoSC（385 字形简体）可作安全回退；完整中文字体需跨版本注入
- 组件：LocalizationText（idText 键 → CSV 取文本）+ TMP/UGUI 显示
- 场景文本：TMP m_Text（写回前确认是否被游戏代码当键）
