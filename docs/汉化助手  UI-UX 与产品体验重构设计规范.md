# 汉化助手 1.0 UI/UX 与产品体验重构设计规范

## 1. 文档定位

### 1.1 产品名称

**汉化助手**

副标题：

> Unity 游戏智能汉化工具

英文产品定位建议：

> **Localization Studio for Unity Games**

---

## 2. 产品重新定位

当前产品已经具备：

- Unity 游戏检测
- 文本提取
- 文本审校
- 批量翻译
- 本地 Hy-MT2 模型
- 术语表
- 翻译质量检查
- 写回游戏
- 基础任务流水线

但当前界面仍然偏向：

> 「工程工具 / 后台管理工具」

目标版本应该升级为：

> **「专业 AI 游戏本地化工作台」**

产品核心不再是：

> 找到文本 → 翻译文本 → 写回游戏

而应该是：

> **游戏接入 → 文本理解 → 智能筛选 → 上下文分析 → AI 翻译 → 语义审核 → 术语一致性 → 质量门禁 → 人工确认 → 安全写回 → 验证**

因此 UI 设计必须围绕整个「本地化工作流」展开，而不是围绕几个独立功能页面展开。

---

# 3. 产品设计目标

本次重构必须同时满足六个目标。

### 3.1 高端

用户第一次打开软件时，应感觉这是一个成熟的专业软件，而不是个人开发工具。

视觉关键词：

- 专业
- 克制
- 科技
- 游戏开发
- AI
- 精致
- 稳定

---

### 3.2 高效率

用户面对几千到几万条文本时，不应该感觉自己在操作 Excel。

必须支持：

- 快速搜索
- 快速筛选
- 批量操作
- 快捷键
- AI 自动处理
- 高风险优先
- 上下文查看
- 翻译记忆
- 一键采用 AI 建议

---

### 3.3 高信息密度

汉化工具不是娱乐软件。

不能为了好看而大量留白。

目标是：

> **专业页面高信息密度 + 首页适度留白**

尤其是文本审校页面，需要尽可能在一个屏幕中看到：

- 原文
- 译文
- 状态
- 来源
- 上下文
- 风险
- AI 分析
- 操作

---

### 3.4 智能

AI 不应该只是一个「开始翻译」按钮。

AI 应该贯穿：

- 文本分类
- 语义判断
- 上下文分析
- 翻译
- 翻译候选
- 质量评分
- 术语推荐
- 风险识别
- 格式检查
- 错误修复

---

### 3.5 可解释

AI 做出的判断不能只有：

> AI：92 分

而应该告诉用户：

> 为什么是 92 分？

例如：

> 「Resume」位于 Pause Menu，并且上一操作为 Pause，因此判断为“继续”，而非“简历”。

---

### 3.6 安全

汉化工具涉及大量原始游戏文件。

任何自动写回操作都必须具备：

- 自动备份
- 写回前检查
- 写回后验证
- 回滚
- 错误报告

---

# 4. 核心设计原则

## 4.1 不再以“页面”为中心，而以“任务”为中心

用户真正想完成的是：

> 「把这个游戏汉化并确保质量。」

因此整个软件应该围绕：

**项目 → 工作流 → 文本 → AI → 质量 → 写回**

组织。

---

## 4.2 不追求“颜色更多”，追求“语义更多”

颜色必须有明确含义。

建议建立：

| 颜色 | 含义 |
|---|---|
| 青绿色 | 产品主色 / 当前操作 |
| 紫色 | AI / 智能能力 |
| 蓝色 | 信息 |
| 绿色 | 成功 / 已通过 |
| 琥珀色 | 警告 / 需要注意 |
| 红色 | 错误 / 高风险 |
| 灰色 | 禁用 / 跳过 |
| 黄色 | 待人工确认 |

颜色必须服务于信息层级，而不能作为装饰。

Fluent 2 的设计规范同样建议把品牌色、语义色和中性色分开，并且避免滥用品牌色；语义色应该用于表达状态，而不是纯装饰。

# 7. Design Token

不要在代码里大量直接写：

```text
#48E6C1
#0D1424
16px
12px
8px
```

必须建立 Design Token。

Fluent 2 也采用 Global Token + Alias Token 的方式，把颜色、字体、圆角、间距、动画等统一管理，以保证不同页面和主题的一致性。

建议：

```text
color.background.app
color.background.surface
color.background.elevated

color.text.primary
color.text.secondary
color.text.tertiary

color.brand.primary
color.ai.primary

color.status.success
color.status.warning
color.status.danger
color.status.info

radius.sm
radius.md
radius.lg
radius.xl

space.xs
space.sm
space.md
space.lg
space.xl
```

这样以后改主题只需要修改 Token。

# 28. Resume 示例

对于：

> Resume

AI 不应该直接给：

> 简历

而应该展示：

```text
Resume

候选词：

简历        12%
继续        86% ✓
恢复         2%
```

上下文：

```text
UI：Pause Menu
前项：Pause
后项：Settings
```

最终：

> 推荐：继续

并显示原因：

> 当前位于暂停菜单，Resume 与 Pause 构成游戏控制语义，因此应翻译为“继续”。

这类解释是你的 AI 汉化产品非常重要的差异化能力。

# 90. 最终产品设计原则总结

整个软件最终遵循以下原则：

> **少边框，而不是少信息。**

> **少装饰，而不是少层次。**

> **颜色表达状态，而不是装饰页面。**

> **AI 提供判断，而不是只提供按钮。**

> **首页展示项目状态，而不是堆功能。**

> **文本中心解决效率，而不是模仿 Excel。**

> **质量中心解决信任，而不是只显示一个分数。**

> **写回必须安全，而不是简单覆盖文件。**

> **知识库负责长期一致性，而不是单纯存几个术语。**

> **用户应该处理 AI 无法确定的问题，而不是重复 AI 已经完成的工作。**

# 94. 最重要的最终结论

这次重构不要简单理解成：

> 「把现在 UI 做得更漂亮。」

真正目标应该是：

> **重新设计“用户如何完成游戏汉化”这件事。**

视觉只是第一层。

第二层是：

> **信息架构**

第三层是：

> **工作流**

第四层是：

> **AI 决策**

第五层是：

> **质量控制**

第六层是：

> **安全写回**

因此最终的汉化助手应该形成一个闭环：

**接入游戏**

↓

**理解游戏**

↓

**发现文本**

↓

**自动分类**

↓

**AI 翻译**

↓

**上下文理解**

↓

**语义审核**

↓

**术语一致性**

↓

**质量检查**

↓

**人工处理高风险文本**

↓

**质量门禁**

↓

**自动备份**

↓

**写回游戏**

↓

**验证**

↓

**完成**

用户最终不是在“翻译 3415 条文本”。

而是在：

> **监督一个 AI 本地化系统完成 3415 条文本。**

这应该成为汉化助手 1.0 重构之后最核心的产品理念。
