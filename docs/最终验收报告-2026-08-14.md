## 三、问题清单

### P2（应修复后发布）—— 1 项

**Q1. 混文数字一致性无确定性检测**
- 严重程度：**P2（中）**
- 复现步骤（实测证据）：
  - `"Deal 50 damage" → "造成 15 点伤害"`：质量门 reasons=[]（数值变化 50→15 未被检出）
  - `"10% boost" → "提升 10"`：质量门 reasons=[]（百分比丢失未被检出）
  - `"Score: 1.5" → "得分：15"`：质量门 reasons=[]（小数位变化未被检出）
- 原因：quality.py 的确定性规则覆盖 placeholder/Rich Text/换行/按键/未翻译，但**没有数字一致性比较**（数字只在占位符 `{0}` 内被 protect）；当前仅靠审核 prompt 维度 7（幻觉：编造数字）概率覆盖，且本地模型（1.8B）对数字改写的检出率无保障
- 修复建议：quality.py 增加确定性规则——原文与译文的阿拉伯数字 token 序列（`\d+(?:\.\d+)?(?:%)?`）必须子序列一致（允许 50→五十 的中文改写，但 15≠50、10%→10 必须失败），类似 input_token_mismatch 的子序列实现，投入约 30-60 分钟
- 验证：修复后本报告 Q1 的 3 个复现用例应全部 reasons 含 `numeric_mismatch`

### P3（低，可发布后修复）—— 3 项

**Q2. 多义词种子表与计划字面预期不一致（2 处）**
- 严重程度：P3
- 复现步骤：
  - `evaluate_entry("Rank", "等级")` → 实际 **0 分 LOW 直通**（计划第十阶段预期 MEDIUM「进入进一步判断」）；rank 不在 `_POLYSEMY_WORDS` 种子表
  - `evaluate_entry("Charge")` 无语境 → 实际 **35 分 MEDIUM**（计划预期 HIGH 人工）；只有命中错误模式（Charge→收费）才升 58 分
- 原因：种子表是固定的 12 词保守集（resume/save/load/charge/quit/options/attack/guard/run/skill/start/press），计划文档以 Start/Rank/Charge 为例示意等级语义，两者未严格对齐；Start 语境消歧后 0 分 LOW 实测通过（与计划 LOW 语义一致）
- 影响评估：无放行风险——MEDIUM 已进本地模型二次审（非自动直通），HIGH 与 MEDIUM 的区别是「人工」vs「本地二查」；Rank 直通是唯一轻微风险（等级/排名/军衔歧义无门禁），但真实游戏数据中 Rank 通常带语境（Character Rank 等）
- 修复建议（可选）：`_POLYSEMY_WORDS` 增补 `rank`（+35 分 MEDIUM）；Charge 无语境升级语义已在 Case 5 错误模式链中覆盖，不建议为对齐计划字面而提高基线

**Q3. Case C（消费者配置）在 fallback 兜底命中时不报告**
- 严重程度：P3（语义差异，非缺陷）
- 复现步骤：主字体缺字形 + fallback 命中 OK 时，`consumer_ok=False` 不触发 CONSUMER_MISCONFIG（实测返回 OK）
- 原因：verify_chain 的 consumer 检查在主字体直接命中路径执行；fallback 兜底命中时渲染链整体可用，消费者引用语义被视作已满足——设计取舍
- 影响评估：fallback 兜底命中即「能渲染」，与「消费者是否引用本资产」是两层问题；文档说明即可

**Q4. 验收计划 6.5 Context Budget 的 glossary 全量注入路径**
- 严重程度：P3（实测已满足预算语义）
- 复现步骤：120 条审核沉淀（candidate）→ format_for_prompt 注入 **0 行**（实测 PASS）；known_names 120 个 → 注入 50 个（实测 PASS）；term_hint 50 对 → 注入 20 对 + 400 字符截断（实测 PASS）
- 说明：glossary 的 active 筛选（跨游戏激活/组合词）本身就是预算门禁——candidate 不注入；计划「10/100/1000/10000 条不整库进上下文」的语义由 active 门槛 + [:50]/[:20]/[:400] 三重截断实现，实测满足

## 六、未覆盖区域（如实声明）

1. **无实机测试**（用户 2026-08-12 指令）：字体/TMP 在真实 Unity 引擎 + 目标设备上的**实际渲染**未验证——静态全链验证器保证数据层正确（码点→字形→图集→fallback 链），但「Unity 实际能够正确渲染」只能在实机确认
2. **无云端语义审核**（用户指令）：语义质量完全依赖本地模型 + 人工池，无云端大模型交叉验证
3. **性能基准**（23 阶段）：未测 5 万-10 万条提取/检索/embedding/翻译耗时与内存、GPU 占用——真实游戏规模（千条级）已闭环，但未做量产级压力
4. **embed/rerank 模型服务**：向量召回/重排路径依赖外部模型服务，本次验收未端到端跑通（能力缺失时自动降级，已有降级测试）
5. **GUI 交互手测**：UI 测试为自动化驱动（test_ui_workbench 54 / test_ui_interactions 31），未做人工点击流程验收
