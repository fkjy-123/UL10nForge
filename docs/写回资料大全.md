| 层级 | 风险 | 现状 |
|---|---|---|
| **二进制结构** | 写回改变对象布局/对齐/长度头,Unity 解析错位 → 资源损坏 | ✅ 已有重开验证兜底 |
| **字符串内容** | 译文比原文短时固定容量池(IL2CPP/Mono #US)尾部 \x00 填充,记录长度不更新 → **运行时字符串带尾部 NUL**,精确比较失败 → **游戏逻辑 bug**(实证) | ❌ **未覆盖,本次 P0** |

## 一、网络文献搜集(4 路并行研究)

> 研究 agent 于 2026-08-09 并行执行,结果陆续并入本节。

### 1.1 路 A:Unity 序列化文件/AssetBundle 写回坑(已完成,7 大主题)

**主题一:Unity SerializedFile 内部结构(11 条)**

1. **字符串字段(4 字节长度前缀 + 4 字节对齐)——汉化写回的核心规则**:MonoBehaviour/TextAsset 内嵌字符串布局为 UTF-8/UTF-16 字节 → 前置 4 字节(小端)长度 → 补零到 4 字节对齐;长度与对齐写错必崩(序列化器按错误边界读取后续字段)。→ 本项目 `_patch_serialized_string` 已实现对齐处理。([汉化笔记](https://www.shuzhiduo.com/A/lk5ak9Zqz1/))
2. **对象绝对偏移 = header.dataOffset + ObjectInfo.byteStart**:写回时若重排/插入数据却不重算每个 byteStart,游戏按旧偏移读对象 → 崩溃。→ 本项目不动布局、原位覆盖,天然规避。
3. **4 字节对齐规则(v≥14):对象表、file identifier 表、每个 pathID 前**:漏对齐会插入/错位字节,元数据区整体偏移。
4. **pathID 位宽与对齐的版本分界(v14)**:v14 之前 pathID 是 32 位且不对齐;v14 起 64 位并强制 4 字节对齐;新工具按错误规则写老文件必错。
5. **大端(endianess)标志:仅 v≥9 位于头字段,更老版本在 metadata 末尾**:无视端序标志按小端写回大端文件,所有 int/long 全部翻转。
6. **类型树(TypeTree)是可选的——独立游戏成品通常无类型树(typeless)**:无类型树文件写回时必须"猜 tree";猜错结构写回,引擎按真实 class 布局读取 → 数据错位。→ **F4(typeless 上 typetree 写回风险)的文献依据**。
7. **TypeTree 紧凑块格式(v==10 或 v≥12):numNodes + stringBufferSize + 字符串缓冲偏移(bit31 指向全局缓冲)**:写回工具按错误版本解析/重建 TypeTree,写出的类型树损坏,引擎加载即反序列化失败。
8. **无类型树打包(DisableWriteTypeTree)会导致加载崩溃——官方实证**:与写回场景同构——任何让运行时"没有类型信息可对照"的写回产物,都会触发同一类反序列化失败。([Unity IssueTracker](https://issuetracker-mig.prd.it.unity3d.com/issues/loading-textmesh-pro-prefab-from-assetbundle-crashes-editor-when-buildassetbundleoptions-dot-disablewritetypetree-option-is-used))
9. **SerializedFile 版本映射表(v5→v15)**:写回工具若按错误的 format version 分支解析头/元数据 → 结构错读。
10. **元数据字符串(版本号等)是 null 结尾、无对齐填充**:与对象内字符串不同,写回工具若按"长度前缀+对齐"规则改写元数据字符串 → 文件头损坏。
11. **pathID 必须唯一,重复即损坏**:写回时若意外复制/合并对象产生重复 pathID,引用解析歧义 → 加载失败。

**主题二:UnityPy 保存/写回已知坑(11 条)**

1. **save_typetree vs save_raw:前者按类型树重建序列化(可能改变字节长度/布局),后者原字节直写**:MonoBehaviour 无 tree 时只能用 raw;官方 README 明确 MonoBehaviour 结构"可能不在 assets 中",是 raw 回退路径的典型场景。→ 本项目 `_patch_asset` 已按「有 typetree 走 save_typetree、无 typetree 走 raw 直写」分发。
2. **缺 typetree 时 save_typetree → 文件损坏、游戏启动冻结**(UnityPy Issue #195,Oxenfree 2):基于残缺 tree 重建的对象字节与真实布局不符,引擎反序列化器读到不存在的字段 → 卡死。([UnityPy #195](https://github.com/K0lb3/UnityPy/issues/195))
3. **TypeTreeGeneratorAPI 生成的"猜测 typetree"有误 → 读写报字节数不匹配**(Issue #322):猜 tree 与游戏实际 class 布局不一致,写回后引擎按真实布局读 → 数据错位/崩溃。
4. **read 失败被吞掉后照常 save —— 半损坏产物**:读必须完全成功,save 才有意义。→ 本项目 `_patch_asset` 的 try/except 结构需要审计:读取异常时是否继续写回。
5. **保存超过 4GB 的文件 → struct.error 溢出**(Issue #229):写 bundle 头用 32 位无符号数溢出 → 文件截断,游戏加载即崩。
6. **TextAsset 的 m_Script 以 str 暴露,需 surrogateescape 保字节**:直接用普通 utf-8 编解码会把非法序列替换成 U+FFFD,写回后文本字节被破坏。→ **F3(TextAsset strict-decode 保护)的文献依据**。
7. **外部引用(FileIdentifier):PathName 必须精确匹配 bundle 内节点**:写回改名或路径变化 → 引用断裂,StreamingInfo 指向的文件不存在 → 资源加载失败。
8. **pathID 跨版本漂移:游戏更新后旧替换文件失效**(UABEA #426):整体替换对象时 pathID 对不上 → 引用错乱。
9. **StreamingInfo(offset/size/path)被工具改写 → 外部 .resS 数据引用破坏**:汉化圈手工做法是按 offset+size 去 .resS 精确覆盖数据(要求新数据 ≤ 原 size)。→ 本项目 font_replace 的 atlas 内嵌方案(StreamingInfo.size=0 + 内联数据)正是此规则的实现。
10. **m_Script 的 fileID/guid/pathID 绑定 —— 改错即 missing script**:MonoBehaviour 靠 m_Script 引用 MonoScript(Assets 内脚本固定 fileID=11500000 + guid;DLL 脚本用库内 fileID);改坏引用 → 组件变空壳,行为丢失甚至空引用崩溃。→ 本项目 `_IMMUTABLE_FIELD_NAMES` 已保护 m_Script 相关字段。
11. **API 改名(1.x → 2.x):save_typetree → patch**:按旧教程写的写回脚本在新版库上行为变化或直接报错。

**主题三:AssetBundle 结构(11 条)**

1. **UnityFS 头字段与 flags(压缩方法 / info block 位置)**:写回时改 flags/头字段与真实数据不符,引擎解压逻辑错乱 → 整个 bundle 解析失败。→ 本项目重建 bundle 时保持头字段与原始一致。
2. **cab-<32hex> 是内嵌 SerializedFile 名,必须原样保留**:写回工具重建 bundle 时若改变 cab 名 → 引用断裂,引擎用 cab 名定位内嵌文件。
3. **blocks info 内嵌 SHA1 校验(前 20 字节为剩余数据哈希)**:写回工具重算 info block 时若哈希不对,依赖严格校验的解析/加载路径直接拒绝。→ 需审计 UnityPy 保存是否重算(它内部处理,一般自动)。
4. **未压缩 bundle 要求 16 字节对齐**:写回时破坏对齐,引擎按错误偏移读数据块 → 数据错位/崩溃。→ UnityPy 保存自动处理。
5. **CRC 只在调用方显式传参时校验;Addressables catalog.json 的 CRC 必须清除**:Addressables 的 catalog.json 带 CRC,改过 bundle 后不匹配 → bundle 不加载;普通零售游戏默认不校验(GBAtemp 实证)。→ **本项目 `_update_addressables_catalogs` 正是这条的实现,文献证实方向正确**。([Unity Manual](https://docs.unity3d.com/6000.4/Documentation//Manual/AssetBundles-Integrity.html))
6. **LZMA 整流压缩 vs LZ4 分块;改过的 UnityFS 无需重压,Unity 接受未压缩 bundle**:写回工具重压缩算法/参数与原始不同 → 引擎解压失败;反之不必重压时乱压反而引入问题。→ 本项目重建时保持原始压缩设置。
7. **manifest 中的 hash 不是文件内容哈希,不能用于校验修改**:是版本标识而非内容校验。
8. **"sharedassets0.assets is corrupted! [Position out of bounds!]" —— 反序列化布局不匹配**:该报错几乎总意味着 bundle 数据布局与引擎预期不符(而非磁盘损坏),修改过的文件最常见触发。
9. **UABE 导入 raw 文件截断 bug:丢最后几个字节,JSON 右花括号消失 → 卡加载**(GBAtemp Dokapon UP! 实证):真凶不是 CRC,而是 UABE 把导出的 raw 文件改后导回时截断末尾字节;这是"工具本身损坏文件"的典型实证。
10. **版本不匹配:游戏更新后旧 modded 文件崩溃**:游戏热修常改动 sharedassets0.assets,更新后旧汉化文件与新版本布局不兼容 → 加载崩溃。→ 提示:本工具对 staging 源做写回,版本错配风险天然低(基于游戏当前文件)。
11. **Addressables catalog.bin "Invalid header data" —— 替换引擎 DLL 后反序列化失败**(BepInEx #1126):二进制序列化依赖精确的运行时类型布局,任何一环不匹配即全链崩溃。

**主题四:Unity 4.x / 5.x / 2017 老版本特有坑(5 条)**

1. WebFile(.unity3d WebPlayer):UABE V3.0 保存后不能运行,必须用 ABE 2.2 再压缩;WebFile 的合并/布局与 UnityFS 不同。
2. 老版本端序字节位置不同(v<9 在 metadata 末尾,且无端序字段前导的 3 个 reserved 字节)。
3. Unity 4.x(格式 v10-13)的 EnableTypeTree 读取规则与 v14+ 不同;v11/v12 官方映射表空缺,工具支持度差。
4. Unity 5.5.3p1 + UABE 2.1d → Access Violation(UABE #157):工具对特定引擎版本的序列化兼容性缺陷。
5. 老版对齐差异:pre-v14 pathID 无 4 字节对齐、32 位;新工具写回会按新规则插对齐字节 → 老游戏读偏移错位。

**主题五:游戏能启动但行为异常(无崩溃但逻辑坏,14 条)**

1. **字符串比较失败:ordinal vs culture、土耳其 i 问题**:`string.Equals` 默认 culture 敏感,`==` 默认 ordinal;汉化后游戏代码里对英文原串的硬编码比较匹配不上 → 分支走错、功能失效。→ **「代码把显示文本当逻辑键」的机制细节**。
2. **TextMeshPro 图集缺字形 → 豆腐块;缺省略号字符 → "Line breaking recursion max threshold hit"**:TMP 静态图集不包含中文字形 → 全部渲染为方框;Overflow=Ellipsis 且字体无省略号字符 → 无限换行递归报错。([Unity #19508](https://issuetracker.unity.com/issues/19508/line-breaking-recursion-max-threshold-hit-error-when-overflow-is-set-to-ellipsis-with-fonts-missing-the-ellipsis-character))
3. **TMP 字体替换改 PathID/GUID → 启动红条警告 + 崩溃**:手动改 m_Script/m_Material/Texture2D 的 PathID/GUID 替换 TMP 字体后崩溃;建议用参数迁移工具而非手改引用。→ **本项目 font_replace 通过替换 bundle 内 TMP_FontAsset 对象而非改引用,正是文献建议的做法**。
4. **编码:BOM 残留在 TextAsset.text、GBK/ANSI 被当 UTF-8 读 → 乱码/解析异常**:写回时 BOM/编码不对 → 游戏代码 JSON/XML 解析失败、显示乱码。→ 与 1.4 路 D 的 A 主题重叠。
5. **事件系统失灵:替换 prefab/资源后 Inspector 事件绑定断裂**:UnityEvent 通过 Inspector 引用绑定,替换/重排资源后目标引用丢失(显示 None)→ 按钮点击无反应且无报错。
6. **硬编码字符串绕过本地化管线 → 部分 UI 永远原文**:汉化只改资源表,代码里硬编码的字符串无法被覆盖;行为上不崩,但游戏内出现"半中半英"。
7. **字体覆盖失败:"□□□" + "Could not find an appropriate asset bundle load method"**(XAT #686/#720):自定义 TMP 字体 bundle 加载方法不匹配 → 全部显示方块。
8. **Localization + Addressables 退出崩溃:"Attempting to use an invalid operation handle"**:仅本地化某个 UI 对象就在退出时崩溃,Addressables 释放 AsyncOperationHandle 出错。
9. **卡 99% 加载:Notepad++ 静默改了文件编码**(3DM 案例):编辑器编码问题,同时证明"改完没效果/卡住"未必是工具问题。
10. **文件大小守恒原则:只能改原长度内文本,不足补空格/零**(GBAtemp 实证"等长替换成功、变长替换失败"):变长写入会破坏后续数据布局。→ **本项目固定容量池(_fit_bytes 填充)正是这条铁律的工程化;F1 修复使其从"填 NUL 且长度字段不更新"升级为"长度字段同步更新"**。
11. **反作弊/完整性校验:hash 校验不过 → 游戏拒绝运行或延迟退出**(GuardingPear/ACTk/自定义 MD5):汉化文件任一字节变化 → 校验失败直接退出或延迟 5-10 分钟退出。
12. **Addressables 初始化期切语言 → 字典 key 冲突崩溃**:InitializationOperation.Completed 中 SetSelectedLocale,bundle 仍留在 m_ActiveBundles,再次 Add 同 key → ArgumentException。→ 与 1.2 路 B 主题 9 重叠。
13. **重复 bundle 名 → 引擎报错/游戏崩溃**:引擎内部按名字缓存/解析 bundle,重名导致解析错乱。
14. **贴图替换导致崩溃但 TextAsset 修改正常 —— 工具/插件差异**(UABEA #448):纹理插件对特定引擎版本的序列化兼容性缺陷;"工具写回路径本身可能损坏文件",需对每种资源类型验证。

**给写回模块的关键结论(归纳)**

1. 字符串写回必须遵守:4 字节小端长度前缀 + UTF-8 字节 + 补零到 4 字节对齐。
2. MonoBehaviour 无 typetree 时绝不走 save_typetree,必须 raw 直写;read 失败禁止继续 save。
3. 任何"重写全文件"的操作都是高危操作:重排对象、变长数据会牵动 byteStart/dataOffset/pathID 全链;优先原地改写或精确补丁。
4. 引用类字段(ExternalReference、StreamingInfo、m_Script、cab- 名、pathID)是最大雷区,碰了就崩或静默失灵。
5. 编码与字节保真:TextAsset 用 surrogateescape 保字节;无 BOM UTF-8 是最安全写回格式。
6. 文件/版本兼容:格式版本分支、端序标志、对齐规则都必须按版本正确分发;bundle 头与 info block 哈希、Addressables catalog CRC 需同步处理。
7. "游戏能启动"不等于"写回成功":字符串比较、TMP 字形、事件绑定、编码乱码都是静默失败面,必须列入验收清单。

### 1.2 路 B:汉化致 UI 交互/崩溃社区实证(已完成,45 条)

**主题 1:中文社区实证案例(3DM/贴吧/B站/CSDN/52pojie)**

1. **补丁与游戏版本错配 → 黑屏/进程挂起/窗口不出现**:汉化替换基于旧版,更新后逻辑地址/资源布局已变,启动阶段加载即失败。([二之国2](https://bbs.3dmgame.com/archiver/tid-5952761.html) [辐射4](https://bbs.3dmgame.com/archiver/tid-6512921.html) [仙女座](https://bbs.3dmgame.com/archiver/tid-5545496.html))
2. **关键词字段被改 → 游戏直接崩溃**:《时之书》JSON 文本中关键词字段不能翻译,游戏代码用关键词做逻辑匹配,改后匹配失败走异常分支/解引用空值。([贴吧](https://tieba.baidu.com/p/8577288705))
3. **字符串前有长度信息字段,只改内容不改长度 → 文字不显示/按键无反应**:程序按长度分配缓冲读取。([3DNes 案例](https://yooqur.com/thread/554583-1.html))
4. **译文超原长度 → 被固定字节读取截断**:汉字 UTF-8 每字 3 字节,程序按固定字节数读串,超出部分被截断。([52pojie](https://www.52pojie.cn/thread-1927454-1-1.html))

### 1.3 路 C:Mono 程序集/IL2CPP 写回坑(已完成,36 条)

**主题 1:ECMA-335 #US 堆结构(9 条)**

1. **长度前缀是 1/2/4 字节压缩整数,不是固定 4 字节**:短串(≤127 字节)只有 1 字节前缀,只有 >16383 字节才用 4 字节;按"固定 4 字节"解析/写入必错位。([SO](https://stackoverflow.com/questions/64948920/understanding-how-ldstr-gets-string-literal))
2. **ldstr token 的 24 位是 #US 堆内字节偏移,原位改长(短)字符串会让后续所有偏移失效**:token `0x70xxxxxx` 直接存堆内字节偏移,堆里任何一个字符串长度变化都会使后续字符串的物理位置漂移。→ 固定容量原位覆盖安全的前提是"数据长度不变";本项目修复后仅缩短不移动,后续记录仍按各自偏移定位,不受影响。([reverseengineering.SE](https://reverseengineering.stackexchange.com/questions/25814/structure-of-operand-bytes-in-net-call-and-data-access-il-instructions))
3. **每条目 = 长度前缀 + UTF-16 数据 + 1 字节标志尾,总字节数恒为奇数**:长度计的是字节且包含尾部标志字节;按偶数对齐读写会错位。
4. **尾部标志字节规则:写中文必须置 1,置 0 是格式违规**:任一字符高字节非 0(所有 CJK 都满足)或低字节落在 0x01–0x08/0x0E–0x1F/0x27/0x2D/0x7F 时,标志必须为 1;把英文串改成中文后不更新标志=违反 ECMA-335。([MS Learn](https://learn.microsoft.com/zh-cn/dotnet/api/system.reflection.metadata.blobbuilder.writeuserstring))
5. **堆内是 UTF-16(16-bit 单元),不是 UTF-8**:中文按 UTF-16LE 每字 2 字节存放;直接贴 UTF-8 字节则每个字符错半。
6. **堆大小上限:ldstr 24 位索引 → #US 整堆可寻址上限 2^24 字节(16MB)**。([roslyn #9852](https://github.com/dotnet/roslyn/issues/9852))
7. **流头(StreamHeader)offset/size 各 4 字节、流大小须 4 字节对齐**:堆变长后流头 size 必须同步更新——本项目原位更新、流大小不变,无需动流头。
8. **堆偏移 0 必须是空 blob(0x00),首个有效字符串从偏移 1 开始**:覆盖偏移 0 字节或把偏移 0 当字符串起点,所有 ldstr 索引整体错位。
9. **改 #US 不碰 metadata 表,但 dnlib 重写有坑:USHeap.SetRawData 可能被静默忽略**:工具可能"以为成功了"而输出没变。([SO](https://stackoverflow.com/feeds/question/29543935))

**主题 2:签名(strong name / Authenticode)(4 条)**

10. **strong name 签名失效:.NET 运行时拒绝加载**(FileLoadException);dnlib/dnSpy 修改后 PublicKey 仍在但签名与内容不匹配。
11. **但 Mono(Unity Mono 内核)历史上不校验 strong name**:SUSE Bug 351740 明说"Mono 运行时不做 strongname 校验";"不挂"不可依赖,行为随 Mono 版本漂移。([SUSE](https://bugzilla.opensuse.org/show_bug.cgi?id=351740))
12. **Unity 的 Assembly Version Validation:Mono 对强命名程序集按精确版本匹配**:引用版本与本地不一致就拒绝加载(Missing Scripts)。→ 修改 DLL 不得动 AssemblyVersion。
13. **Authenticode:改 Unity 独立版任何资源即失效,Mono 自己的 Authenticode 校验还有 bug**:个别游戏用 X509Certificate.CreateFromSignedFile 自校验程序集。([Unity discussions](https://discussions.unity.com/t/unity-5-the-digital-signature-is-not-valid-when-using-a-custom-icon-in-windows/581537))

**主题 3:IL2CPP global-metadata.dat 结构(6 条)**

14. **magic 0xFAB11BAF + 版本号被破坏 → 启动即崩**:MetadataCache::Initialize 校验 sanity 与版本;任何误改头部/版本不匹配,初始化元数据阶段直接闪退。→ 写回绝不触碰 header 区。
15. **header 是约 35–40 对 (offset, count),stringLiteralCount 是"字节数"不是"条数"**:计数要除以 8 才是条数;用错版本布局解析,所有偏移错位。→ 本项目 _LAYOUTS 按版本硬编码 entry_size,已规避。
16. **stringLiteral 条目 = {dataIndex uint32, length uint32},小端序,length 是字节数**:写入奇数 length 或把字符数当字节数写,运行时按 length 复制即错。([Cpp2IL wiki](https://github.com/SamboyCoding/Cpp2IL/wiki/IL2CPP-Data-Structures))
17. **版本差异巨大:24/27(2020.2 起 usage 方式变化)/29(2021.2)/31(2022.3)/32(2023.1)**:Unity 大版本几乎必改布局;用错版本解析器读 metadata,偏移全错,修改工具按错偏移写回,游戏崩溃。→ 本项目仅支持已验证版本,未知版本直接拒绝。
18. **stringLiteralData 区紧凑排列、无 \0 分隔符,靠 dataIndex+length 取用;变长修改必须重建整个数据区并更新所有相关条目的 dataIndex,只改一个条目必坏**:一个字符串变长原位写超界,会把后面字符串的头几个字节覆盖,后续字符串静默损坏。→ **F1 修复的 v39 链式重建正是此结论的落实**。([binmt](https://bbs.binmt.cc/forum.php?mod=viewthread&tid=161737) [patcher](https://github.com/jozsefsallai/il2cpp-stringliteral-patcher))
19. **加密/加壳 metadata(防破解游戏):直接改文件=破坏密文结构**:AntiCheat+AppGuard 双保护、把 GetStringLiteralFromIndex 换成解密函数的游戏,文件被加密/混淆;必须先内存 dump 解密版再改。→ 本项目提取阶段解析失败的 metadata 天然跳过,写回不可达,已安全。

**主题 4:字符串引用、dataIndex 与 hash map(4 条)**

20. **代码引用的是"字面量索引"而非地址——改内容不破坏引用,改坏条目才全挂**:运行时 GetStringLiteralFromIndex(index) 按索引取条目再取数据;字符串内容可改,只要条目(dataIndex/length)与数据区一致。→ **F1 修复的理论依据:更新 length 字段/重建 dataIndex 是安全且唯一的正确做法**。
21. **固定容量原位改长 → 覆盖后续字符串的头几个字节**:数据区无 \0 分隔,一荣俱荣一损俱损;等长修改安全,变长必须追加到文件尾部并改 header 与条目。→ 本项目 _fit_bytes 强制译文 ≤ capacity(只缩短),原位安全。
22. **stringLiteralHashMap 是运行时懒加载的"索引→Il2CppString*"缓存,不改内容也没关系**:缓存按索引键控,不按内容 hash;il2cpp-stringliteral-patcher 跨版本(v29)成功改写且官方论坛确认改值无需重新生成 C++。→ 无需重算任何 hash。
23. **Il2CppDumper 的 dump 只验证"能解析",不验证"运行时一致"**:以"dump 正常"作为改写成功的判定,会漏掉头部损坏、版本不符这类启动即崩的错误。→ 本项目用"重开重新解析 + 逐条字节比对"验证,比 dump 严格。

**主题 5:编码与转义(4 条)**

24. **IL2CPP stringLiteralData 社区资料称是 UTF-16LE**:注意——社区资料(Cpp2IL/patcher 工具链)指向 UTF-16LE,但本项目 12 个真实 metadata(v24-39)实测 100% UTF-8 可解码,提取/写回均按 UTF-8 与真实样本对齐;差异可能源于 Unity 版本(老版本 UTF-16,新版本 UTF-8)。写回以实测为准,新版本游戏优先;若未来遇到 UTF-16 布局样本,提取时的 strict decode 会自然拒绝。([discussions](https://discussions.unity.com/t/modifying-il2cpp-stringliterals/669332/5))
25. **C# 源码转义与字面量差异:"\n" 编译后是真实换行,不是反斜杠+n**:JSON 工作流的 JSON 解析器同样把 \n 当转义;工具若把"源码文本"按字面写回,游戏显示字面 "\n"。
26. **长度语义都是"字节数":#US 前缀与 IL2CPP length 字段均按字节,不能按字符数**;按字符数写长度=只写入一半,NewLen 复制半个字符。
27. **中文写进去后,游戏内置字体若不含 CJK 字形,显示为方块**:改字符串不解决字体问题,需同步替换字体资源。→ 本项目 font_replace 模块已覆盖。

**主题 6:写回后崩溃/行为异常社区案例(5 条)**

28. Mono:TypeLoadException——dnSpy 编辑保存后类定义偏移错乱、字段/方法 token 被重排,程序集加载阶段即崩。
29. Mono:MissingMethodException / vtable 断裂——改方法签名/参数数量,虚函数表索引错位。
30. Mono:存档损坏——修改涉及 [SerializeField] 字段或它们的 metadata token,存档按旧布局反序列化读档错位(最恶劣)。
31. Mono:InvalidProgramException(混淆未解码)与 FileNotFoundException(依赖不符)。
32. IL2CPP:改后偏移溢出,启动崩溃——字符串区改坏后解析报"偏移溢出",MetadataCache 读越界;只能还原备份或重建索引。([gitcode](https://blog.gitcode.com/7f1a0a657fa120b0b511c4c798b6c0f8.html))

**主题 7:固定容量截断 UTF-16 的字节对齐坑(4 条)**

33. **截断到奇数字节 → 半个 UTF-16 字符被切开**:运行时按 length/2 复制,字符对错位,文本尾部乱码/无效 UTF-16。
34. **截断半个代理对 → 孤立代理(补充平面 CJK 扩展 B、emoji)**:.NET/Mono 字符串变为非法 UTF-16,序列化/再编码时损坏或替换,且不抛异常极难察觉。→ 本项目 UTF-16 截断按 2 字节对齐 + 预留省略号,UTF-8 截断按字符边界,已规避。
35. **固定容量 = 静默截断,译文长于原串时被无声截掉**:hex 编辑器只能等长修改;超长译文被截断且工具无感知——这是"变长重建"工具存在的原因。→ 本项目 _fit_bytes 截断时补省略号并 note_truncated 报告,不静默。
36. **#US 截断是三处联动的:UTF-16 偶数 + 尾标志字节 + 前缀长度,漏一处则下一字符串偏移失效**:一个 bug 毁掉整堆。→ **F1 修复必须同时更新前缀长度与标志字节位置(数据变短后标志不再紧跟数据末尾旧位置,要写到新数据末尾之后)**。

### 1.4 路 D:TextAsset/编码/文本内容风险(已完成,30 条:C/D/E/F)

**主题 C:CSV/TSV 翻译写回风险(8 条)**

1. **译文含半角逗号且未按 RFC 4180 加引号包裹 → 字段被当分隔符,整行列错位、后续列偏移**:游戏按逗号拆列,译文 "Hello, world" 裂成两列,Key/Id 对不上,查表返回空串或错位文本;Unity Localization 官方导入器不支持换分隔符,错位后直接报 "Could not find a header field" 导入失败。([Unity discussions](https://discussions.unity.com/t/serious-csv-import-issues-on-mac-os-list-separator/1518246/3))
2. **字段内双引号按 RFC 4180 应写成 "" 转义,朴素解析器把转义对误判为字段边界**:译文含 "27\" 显示器" 类内容时,朴素解析器把第 2/3 个引号当字段结束符,后续列全部错位;Polars 写回还会过度转义成 """"。([SPARK-20155](https://issues.apache.org/jira/browse/SPARK-20155))
3. **Excel 保存的 UTF-8 带 BOM(EF BB BF),BOM 混入第一列表头成 "﻿Key",字典查键永远查不到**:游戏按表头建字典,首列键名实际是 "﻿Key",索引返回 -1,第一列数据全变 null/空串;字符不可见,报错却指向"表头找不到",极难排查。([seatunnel #10374](https://github.com/apache/seatunnel/issues/10374))
4. **Windows 的 CRLF 与游戏期望的 LF 混用 → 行尾 \r 残留在最后字段("你好\r")**:按 \n 拆行后每行最后一列带 \r,文本比较失败、显示末尾残留;引号包裹字段的末字段若吞掉 \r 则报"缺少结束定界符"解析失败。([CodableCSV #35](https://github.com/dehesa/CodableCSV/issues/35))
5. **某行字段数少于表头列数 → 按表头取列/映射结构越界**:Apache Commons CSV 官方 issue:行字段少于表头时 CSVRecord.toMap() 抛 ArrayOutOfBoundsException;游戏按列索引取值不捕获即运行时崩溃或整行丢弃。([CSV-111](https://issues.apache.org/jira/browse/CSV-111))
6. **Unity 官方 Localization 包 CSV 导入器要求固定表头 Key/Id、固定逗号分隔;旧版本导出的 CSV 自带 BOM**:表头缺 Key/Id 或分隔符被换成分号(欧洲/Mac 导出)即报 "Could not find a header field";官方直到 1.5.0-pre.6 才修掉"导出 CSV 带多余 BOM"问题。([Localization CSV 文档](https://docs.unity3d.com/Packages/com.unity.localization@0.10/manual/CSV.html))
7. **I2 Localization CSV 流程:term 名不允许逗号等符号;Excel 编辑导出会剥引号/改编码导致再导入失败**:翻译者在 Excel 改完保存,Excel 去掉字段引号并改写编码,游戏侧按逗号拆分直接错列或乱码。([I2 手册](http://www.inter-illusion.com/assets/I2LocalizationManual/ImportingaCSVfile.html))
8. **中英文逗号差异:中文规范用全角逗号(U+FF0C),若译文误用半角逗号即撞上 CSV 分隔符**:中文排版强制全角正是为了与数据格式分隔符区隔,本地化检查必须盯住。([fedoraproject 讨论](https://lists.pagure.io/archives/list/chinese@lists.fedoraproject.org/message/H3YBBJ6MRL25OJDQDV2M7ATZTVNLD3TI/))

**主题 D:JSON/XML/INI 翻译写回风险(8 条)**

1. **JSON 字符串内引号、反斜杠、控制字符(U+0000~U+001F)必须转义,RFC 8259 明确 MUST be escaped**:译文原样出现半角引号/换行/控制字符时,游戏侧 JSON 解析(JsonUtility/Json.NET/自定义)整体失败,整段配置读取失败,回退默认值或直接崩溃。([RFC 8259](https://www.rfc-editor.org/errata/eid7673))
2. **Unity JsonUtility 极其严格:不接受单引号、尾随逗号、NaN/Infinity 字面量,报错还怪("Missing a name for object member")**:译文/配置里出现 'xxx' 单引号或末尾多逗号,JsonUtility.FromJson 抛 ArgumentException;游戏加载存档/配置时整个反序列化失败。([SO 67124866](https://stackoverflow.com/questions/67124866/jsonutility-fromjson-keeps-throwing-argumentexception/67127401))
3. **JsonUtility.FromJson 遇损坏/畸形 JSON 不只是抛异常——官方 issue 记录会直接崩溃(RaiseException)**:本地化 JSON 写回坏一行,游戏启动解析即崩溃(官方 Issue 1293534,2019.4/2020.1 上崩溃无堆栈)。([Unity Issue 1293534](https://issuetracker-mig.prd.it.unity3d.com/issues/crash-on-raiseexception-when-calling-jsonutility-dot-fromjson-with-a-corrupted-json-file))
4. **非法代理对(孤立 \uD800 高代理等)被 JSON 解析器拒绝("missing or wrong low surrogate")**:切字符串/乱码转码产生孤立代理对写入 JSON,Python json/nlohmann/Rust 等解析器全部报 parse_error;.NET/Unity 底层 UTF-16 处理同样场景,坏字符一路传染到存档读写。([SO 66011236](https://stackoverflow.com/posts/66011236/revisions))
5. **XML 1.0 禁止控制字符(U+0000~U+0008、U+000B/C、U+000E~U+001F),写入 XML 后 XmlDocument/XDocument 解析直接抛 XmlException "invalid character"**:译文或数据带一个控制字符就整份文档解析失败;U+0000 在 XML 1.0/1.1 全版本一律非法。([baeldung](https://www.baeldung.com/java-xml-invalid-characters))
6. **.NET 系解析器(XmlDocument/XDocument)对编码声明不符、非法字符极敏感("Invalid character in the given encoding"),&amp; 未转义必报错**:Unity 游戏基于 .NET/Mono 用 XmlDocument.Load 读翻译 XML,译文含未转义 & 或声明编码与实际字节不符即抛 XmlException;游戏不捕获就崩溃,捕获则整段配置静默回退。([SO 8275825](https://stackoverflow.com/questions/8275825/how-to-prevent-system-xml-xmlexception-invalid-character-in-the-given-encoding/8275868))
7. **INI 无统一标准:朴素解析器把行内 ';'/'#' 当注释、把值里的 '=' 或引号搞坏(PHP parse_ini_file 截断引号内 ';' 后内容;nanoini 连引号都不认)**:译文/配置值含 "a=b;c" 时,有的解析器取第一个 '=' 前当键、有的把 ';' 后内容截断;同一份 INI 在不同平台/构建解析结果不一致,设置静默丢失。([PHP bug 48769](https://bugs.php.net/bug.php?id=48769))
8. **译文引号/结构破坏直接写回 JSON 本地化文件(如法语 L'épée de l'"héros")→ 游戏启动/场景加载解析失败,崩溃或整批回退默认语言**:实测记录:译文未转义双引号使 json 解析失败、整批翻译中止;dev.to 案例法语引号导致游戏启动即崩;写回工具不做"转义校验+宽容解析兜底"就会把坏文件交还给游戏。([dev.to](https://dev.to/hugo_bernardocardoso_d38/how-to-translate-game-localization-files-json-po-without-breaking-code-variables-2334))

**主题 E:编码写错后的症状(5 条)**

1. **UTF-8 字节被按 Latin-1/ISO-8859-1 解码 → 经典 mojibake(é→"Ã©")**:本地化文本先被某工具按 Latin-1 读入再落盘即双重编码,错误字节以 UTF-8 存储后永远乱码,且按原文 key 查译文全部失败;原始字节没坏,是解码假设错了。
2. **UTF-16 被按 UTF-8 解码 → 字符间全是 NUL(0x00)字节,C/C++ 字符串按首个 NUL 截断**:游戏引擎 C++ 侧用 strcpy/strlen 或按 \0 找结尾的朴素解析器,第一个字符就"结束",表格被静默截断无报错;UTF-16 中 NUL 是字节不是字符,8 位字符串代码无法区分。
3. **UTF-8 内容被按 GBK/ANSI 解码 → "锟斤拷"经典乱码**:无法解码的字节先被替换为 U+FFFD(EF BF BD),再被 GBK 两两配对成"锟斤拷";信息已不可逆损坏;中文 Windows 默认 ANSI 就是 GBK,汉化工具最易踩。([锟斤拷](https://baike.baidu.com/item/%E9%94%9F%E6%96%A4%E6%8B%B7))
4. **无 BOM 的 UTF-16 文件被 .NET 默认按 UTF-8 解码 → 整篇乱码(不崩溃)**:.NET BOM 检测只认 BOM 头,无 BOM 一律回退 UTF-8;游戏静默加载全乱码本地化文本且不抛异常。
5. **错编码后果边界:宽松解码器(File.ReadAllText、浏览器)只出 U+FFFD"乱码不崩";严格解析器(XML/JSON、throwOnInvalidBytes)直接抛致命异常=崩溃**:同一份错编码字节流,显示路径只是 �,喂给 XML/JSON 解析器就抛 "Invalid byte 2 of 3-byte UTF-8 sequence" 之类 fatal error 中断加载;XML 规范把声明编码与实际字节不符定义为 fatal error,"只乱码不崩溃"不代表安全。

**主题 F:Unity/游戏解析文本文件的脆弱点(9 条)**

1. **File.ReadAllText(path) 无参重载是"UTF-8+BOM 检测",Encoding.Default 在中文 Windows 是 GBK(936)——两者混用致 UTF-8 文件乱码**:开发者以为"默认=UTF-8",传 Encoding.Default 时在中文 Windows 按 GBK 解 UTF-8 文件,中文全乱码;同一代码在英文 Windows/Linux(.NET Core 恒为 UTF-8)行为又不同,跨平台必踩。([SO 6825601](https://stackoverflow.com/questions/6825601/whats-the-default-encoding-for-system-io-file-readalltext/20172720))
2. **StreamReader 默认 UTF-8+detectEncodingFromByteOrderMarks:有 BOM 时检测结果覆盖你显式传入的编码,无 BOM 时回退到指定编码**:"我明明传了 Encoding.UTF8 为什么还乱码"——文件带 UTF-16 BOM 时 StreamReader 无视参数改用 UTF-16;BOM 有无×参数形成四象限,四分之一组合出错。
3. **TextAsset.text 返回原始字节解码结果、不做换行归一化:CRLF 文件的 \r 原样保留,Split('\n') 后每行尾残留 \r,字符串比较全部失败**:key "TUTORIAL_1" 实际是 "TUTORIAL_1\r",与代码字面量比较永远不等,查译文返回 null 显示空文本;编辑器换行归一化掩盖了 \r,只在运行时炸。([gamedev](https://gamedev.stackexchange.com/questions/155212/unity-c-file-readalllines-vs-textasset-split-n))
4. **UTF-8 BOM 残留第一个 key/表头:"id" 变 "﻿id",字典查找/列映射全 miss,第一列整列丢失**:朴素解析器不剥 BOM 时查 csv[key] 全部 miss;Excel"另存为 UTF-8 CSV"必然加 BOM,本地化表几乎都从 Excel 来,命中率极高。
5. **Unity 资源管线按"扩展名+BOM 头"推断 TextAsset 编码:非 UTF-8 文件导入即错,官方推荐 UTF-8 无 BOM;带 BOM 的 TextAsset/Prefab 有已知损坏 bug**:TextScriptImporter 在导入期解码并序列化成快照,构建后不再转码,编码错误导入瞬间定型;ASCII 文件甚至可能读成空字符串。([Unity 文档](https://docs.unity3d.com/cn/2018.1/Manual/class-TextAsset.html))
6. **JsonUtility.FromJson 不剥 BOM:JSON 开头带 ﻿ 直接抛 "ArgumentException: JSON parse error: Invalid value",游戏启动/热更加载即崩**:配置/本地化 JSON 被存成带 BOM 后 Unity 内置解析器把 BOM 当非法首字符直接抛异常——是直接崩溃而非乱码。([Unity discussions](https://discussions.unity.com/t/jsonutility-fromjson-error-invalid-value/635192/11))
7. **朴素解析器按 '\n' 切行后,最后字段/行尾带 \r;需 StringSplitOptions/正则 \r?\n 或先 Replace("\r","")**:任何按 \n 切分 CRLF 文件都会在字段尾残留 \r,对最后字段做 Trim/比较/拼接时出错(ID 查表、路径拼接、判空),且只在 Windows 编辑过的文件出现。
8. **本地化 CSV 工具链的"BOM 悖论":无 BOM 的 UTF-8 CSV 在中文 Windows 被 Excel 按 GBK 解成乱码,于是工具链普遍主动加 BOM;加 BOM 又被游戏侧无 BOM 解析器破坏第一个 key——两端互相拆台**:上游(Excel/PM 工具)为显示正常必须加 BOM,下游(游戏解析器)必须剥 BOM 才不坏 key,中间任何一环没对齐就翻车,是本地化流程最常出错环节。
9. **Addressables/Resources 加载路径对文本二次转码:导入时按 ANSI 解码的文本在构建/加载后被改编码,字节被展开(1字节变3字节),本地化文本"加载后变了"**:同一 .txt 编辑器里正常、打包后乱码——不同加载路径(TextAsset 快照 vs Addressables 下载 vs 运行时 File API)编码处理不一致。([Unity discussions](https://discussions.unity.com/t/textasset-addressable-encoding-changes-once-loaded/780577/6))

**主题 G:文本内容本身导致游戏崩溃/异常(10 条)**

1. **超长文本塞进 TMP/UGUI 组件,CPU 端整网格重建,帧率骤降甚至卡死**:汉化后文本变长(中文往往更长),TMP 每次 set text 重跑 2500 行 GenerateTextMesh() 并按字符重建网格;官方已知 bug(IN-94783)布局舍入容差禁用时 FPS 从 300 掉到 30;聊天框/日志类 UI 直接卡死。([Unity issue](https://issuetracker-mig.prd.it.unity3d.com/issues/performance-drops-when-textmesh-pro-ui-layout-rounding-tolerance-is-disabled))
2. **超长 TextAsset 访问 .text 属性,一次性分配巨量内存,移动端 OOM 崩溃**:TextAsset.text 把整个文件解码成 C# 字符串再分配托管内存,大文本瞬时吃满内存,iOS/低端安卓在 UnityGfxDeviceWorker 线程直接 OOM 崩溃。([Unity discussions](https://discussions.unity.com/t/textasset-does-not-load-full-file/1693613))
3. **文本嵌入 NUL(\0):Unity 字符串"长度对但内容截断",进原生层崩溃**:Unity 官方确认(未修复):字符串含 \0 时 Length 报全长度但 Debug.Log/UI 只显示到 \0;含 \0 的字符串经 memcpy/不安全序列化拷给原生代码会堆损坏段错误。([Unity issue](https://issuetracker.unity3d.com/issues/strings-are-not-fully-read-when-slash-0-null-character-is-used))
4. **超长文本交给 C/C++ 固定长度缓冲区或 C 字符串接口:截断+越界写,堆被写坏**:游戏文本常走原生插件,strncpy 不保证补 \0;AXIS2C 真实事故缓冲恰好填满时把 NUL 写到缓冲外、malloc 堆损坏崩溃。([SEI wiki](https://wiki.sei.cmu.edu/confluence/plugins/viewsource/viewpagesrc.action?pageId=88036969))
5. **孤立代理(lone surrogate)进 Unity 字符串,IL2CPP/原生 marshaling 直接崩溃**:Unity 官方多起实证:IL2CPP 字符串 UTF-16→UTF-8 遇非法代理对崩溃(TMP InputField 输 emoji 复现);半个 emoji 传给原生 C++ 代码编辑器直接崩;Windows 上 C# 含孤立低代理让编辑器崩溃或刷数百条错误。汉化工具解码出错产生的孤立代理是常见源头。([Unity issue](https://issuetracker-mig.prd.it.unity3d.com/issues/backport-il2cpp-doesnt-properly-handle-invalid-surrogate-pairs-causing-crash))
6. **孤立代理按 UTF-8 编码时被静默替换成 U+FFFD,译文数据悄悄损坏**:.NET Encoding.UTF8.GetBytes 对孤立代理直接替换 U+FFFD;汉化工具解码失败→再编码时字符不可逆变 �,游戏里大量"�"且原文信息永久丢失。([xunit #2107](https://github.com/xunit/xunit/issues/2107))
7. **含孤立代理/畸形字符的文本进 JSON,序列化报错或解析拒绝**:JsonUtility.FromJson 对坏输入直接抛异常;严格 JSON 解析器对 \uD800 孤立代理直接拒绝;JSON.stringify 后字符串是纯 ASCII 时 isWellFormed() 还返回 true 但解析器照样拒收——孤立代理能绕过简单校验。([Unity discussions](https://discussions.unity.com/t/jsonutility-fromjson-throwing-errors/923116/2))
8. **文本混入 RTL 双向控制符 U+202E 等:显示顺序反转、界面文案错乱**:U+202E(RLO)强制其后字符按 RTL 反向渲染,逻辑字节序不变、视觉顺序反转;漏洞族 Trojan Source(CVE-2021-42574);翻译工具不剥双向控制符,汉化后界面文本倒装是必然。

10. **译文内含 \n / \t / 字面 "\n",灌进单行 label:单行约束失效、显示错乱或显示字面量**:Unity 官方确认:代码里给 TextField 赋含 \n 的字符串时 Singleline 约束被忽略;外部语言包里的字面 "\n" UI 组件不解析转义原样显示;开 Best Fit 时 Unity 忽略所有换行压成一行。([Unity issue](https://issuetracker-mig.prd.it.unity3d.com/issues/singleline-constraint-ignored-on-textfield-when-value-set-in-code-to-string-with-slash-n))

**主题 H:Unity 社区/汉化组/GitHub 工具实战案例与修复经验(9 条)**

3. **汉化后显示"口口"豆腐块:根因多为字体缺字形而非编码(XAT issue #597 实证)**:游戏字体缺 CJK 字形,译文逐字变方块;最常被误判为乱码/崩溃的坑:数据完全正确,渲染阶段没字形;修复要换字体/生成 SDF 而非重做编码。([XAT #597](https://github.com/bbepis/XUnity.AutoTranslator/issues/597))
4. **TextAsset 写回编码不一致(ANSI/GBK vs UTF-8):游戏能启动但全盘乱码**:官方文档明确 TextAsset.text 自动编码探测规则(带 BOM 的 UTF-32/16/8,无 BOM 按 UTF-8 兜底);实战:Windows ANSI 被误判 GBK、Android 又被强制转 UTF-8 双重解码失败全问号;《御曹司》安卓汉化打包后对话框全乱码,修好导出/导入脚本 UTF-8 参数才解决。([Unity 文档](https://docs.unity3d.com/cn/2022.3/ScriptReference/TextAsset-text.html))
5. **改动键名/标识符 → 游戏崩溃;打包后文件大小与原文件不一致 → 卡在初始界面**:《时之书》汉化帖:文件里关键词是程序运行时检测的键名,动一个游戏就崩;《夏日重现》汉化笔记:替换字体后游戏卡死,根因是打包未更新文件大小字段,资源总大小必须与原文件严格一致。([贴吧](https://tieba.baidu.com/p/8577288705) [xzonn](https://xzonn.top/posts/Summer-Time-Rendering-Another-Horizon-Translation.html))

**主题 A:Unity TextAsset 编码(6 条)**

1. **TextAsset.text 对"无 BOM 且非 UTF-8"文件(Windows ANSI/GBK 保存的 .txt)自动解码为乱码或直接返回空字符串,不报错**:官方自动检测只认"带 BOM 的 UTF-32/UTF-16/UTF-8"四种,兜底按 UTF-8 无 BOM 解码;GBK/ANSI 字节流被当 UTF-8 解读产生乱码,且发生在导入期,运行时加载的是已损坏的快照;另有报告 ANSI 文件下 .text 直接返回空串。([Unity 文档](https://docs.unity3d.com/2021.3/Documentation/ScriptReference/TextAsset-text.html))
2. **UTF-16 文件必须带 BOM 才会被 Unity 自动识别;无 BOM 的 UTF-16LE/BE 被当作 UTF-8 兜底解码,双字节交错全变乱码**:社区反复强调"UTF-8 无 BOM 最兼容"的原因。
3. **TextAsset.text 返回的字符串保留 BOM 字符(不像 File.ReadAllText/XmlReader 自动吞掉),直接喂 XmlReader/XmlDocument 报 "XmlException: Text node cannot appear in this state. Line 1, position 1"**:汉化工具写回时加了 BOM(如 Notepad++ 默认 UTF-8-BOM 保存)会让原本能解析的配置全部解析失败。([Unity discussions](https://discussions.unity.com/t/xmlexception-text-node-canot-appear-in-this-state/1268/8))
4. **扩展名不是 .bytes 的文本文件,TextImporter 无法按 UTF-8 解析时会"静默剥离所有非 ASCII 字符",中文在导入期就丢**:官方文档明确写了剥离行为;游戏里 .txt/.json/.xml TextAsset 导入时非 ASCII 字符被静默删除——是"写回后中文消失"的最隐蔽源头。([Unity 文档](https://docs.unity.cn/2018.1/Documentation/ScriptReference/TextAsset-bytes.html))
5. **TextAsset.bytes 返回的字节随文件扩展名和 Unity 版本不同而不同**:官方 IssueTracker 确认非 .bytes 扩展名时返回的 bytes 由 text 字符串再编码派生,原始字节在导入期已被改写(2020.1.0a17 修复);汉化工具以 TextAsset.bytes 为准做字节级替换,不同版本游戏行为不一致。
6. **同一份文本经 Addressable 加载后编码会"变化"(ANSI 文件部分字节被展开成 3 字节 UTF-8 形式),反序列化直接失败**:TextAsset 的字节内容在导入/打包/加载链路中不稳定,汉化工具假定"bytes=源文件字节"会在这类游戏上出错。

**主题 B:TextAsset 在 .assets 序列化文件里的存储(7 条,分版本)**

1. **老版本 Unity .assets 中 TextAsset 文本内容按引擎内部字符串格式序列化——UTF-16 LE 编码、int32 字节长度前缀;直接按 UTF-8 读/写整段乱码**(注:此结论基于社区逆向+格式文档,建议用真实 3.x/4.x .assets 字节验证)。([UnityPack wiki](https://github.com/HearthSim/UnityPack/wiki/Format-Documentation))
2. **TextAsset 的 m_Script 字段在不同版本/TypeTree 下类型不同——新版是 bytes、旧版是 string;UnityPy 旧版 fork 读老文件得到 str,新版得到 bytes,写回时 str/bytes 类型不匹配直接报错**。([mos9527/UnityPy](https://github.com/mos9527/UnityPy))
3. **UnityPy 对旧版 str 类型 m_Script 写回非 UTF-8 二进制必须用 surrogateescape(读 encode("utf-8","surrogateescape"),写 decode 回来),直接赋值原始字节会炸**。
4. **UnityPy 的 .text 属性固定按 UTF-8 解码,对 UTF-16/Shift-JIS 等源内容抛异常或产生乱码,必须走 .script 原始字节自行解码**:日文游戏源文本常为 Shift-JIS,直接取 .text 汉化会把原文破坏(先错误解码再重新编码,原始信息丢失)。
5. **UABE/UABEA 导出-导入 TextAsset 走 .txt 且按 UTF-8 解释,编辑器保存时编码被改动(加 BOM/变 ANSI)导致游戏加载卡死**:3DM 案例:改 assets 后游戏卡在加载界面 99%,定位为 Notepad++ 保存时编码被改变。([3DM](https://bbs.3dmgame.com/forum.php?mod=viewthread&tid=5793115))
6. **Unity 序列化文件中字符串通用存储是 int32 长度前缀(字节数,非字符数)+原始字节;文件头/元数据部分字符串是 null 结尾、无长度前缀;解析错位会读乱整个对象**。([UnityPackFF wiki](https://github.com/dongresource/UnityPackFF/wiki/Serialized-file-format))
7. **老版本 .assets(Unity 3.x/4.x,SerializedFile version ≤10)与 5.x+ 对象布局/TypeTree 结构差异大,工具版本错配字段错位;老文件常无 TypeTree,解析依赖内置类型表**:把老 Unity 游戏当新版解析时,TextAsset 的 m_Script 字段类型(str vs bytes)读错,导出文本为空或乱码。([UnityPackFF wiki](https://github.com/dongresource/UnityPackFF/wiki/Serialized-file-format))

### 2.3 地面真相(UnityPy 源码确认,2026-08-09)

- UnityPy `read_aligned_string`/`write_aligned_string`:**int32 长度头 + UTF-8 字节 + 4 字节对齐**,`"string"` 与 `"str"` 同一实现(EndianBinaryReader.py:146 / TypeTreeHelper.py:49)。→ 当前 rawstr 字节补丁写 UTF-8 正确。
- 提取侧 `scan_strings` 扫描 aligned UTF-8 字符串(extractor.py:494),与写回侧 `_patch_serialized_string`(writer.py:404)编码一致。
- 老 Unity(4.x/5.x)TextAsset `m_Script` 为 str 字段:UnityPy 以 utf8+surrogateescape 读写;当前代码 str→bytes 用 `utf-8-sig` + `surrogateescape`,写回用 `utf-8` 还原(MarioVsLuigi 28 对象实证通过)。

### 2.4 摸底实证发现(真实数据验证,2026-08-09)

**发现 F1(实证,P0):固定容量池截短译文 → 运行时字符串尾部带 NUL**

- 现象:`_fit_bytes` 把短译文 pad `\x00` 到 capacity;`_patch_metadata`/`_patch_dll` 不更新 IL2CPP 记录长度字段 / #US 压缩长度前缀 → 游戏运行时读到的字符串 = 译文 + 尾部 NUL。
- 实测:9 个真实 global-metadata.dat(cosl/seijundrop/doog-hololive-fangame/backrooms/soul-delivery 等)全量命中:`'You're trying to transitio'`(38 字节)写 `'你好世界'` 后 payload = 你好世界 + 27 个 \x00,记录长度仍为 38。
- 后果:C# 字符串按长度精确比较 → `if (text == "Level Complete")` 类逻辑全部失败 → 按键/菜单/对话判定失灵。UI 渲染不可见,测试(中文 startswith 找回)也测不出来——**这是「测试全绿但真实游戏出 bug」的头号嫌疑**。
- 涉及路径:IL2CPP v24/27/29/31(显式长度记录,可修)、v39(隐式长度,需链式移位)、Mono #US(可修当压缩前缀同尺寸类)。

**发现 F2(代码路径确认,P0):截断可能破坏 {0} 占位符 → string.Format 崩溃**

- 质量门在翻译阶段校验占位符完整(quality.py `validate_translation`),但 `_fit_bytes` 的截断发生在写回内部,截断点可能把 `{0}` 切成 `{0` 或去掉 `{1}` → 游戏 string.Format 抛 FormatException → 崩溃。
- 同理:省略号「…」追加位置可能吞掉尾部占位符。

**发现 F3(代码路径确认,P1):TextAsset 非 UTF-8 内容被 decode-replace 污染**

- 提取侧 `_textasset_entries`:二进制过滤(控制字符>5%)能挡 UTF-16,但 **GBK/Latin-1 文本**可能同时通过控制字符过滤与字母密度过滤 → 以 mojibake 原文字符串入库 → 写回侧 `_patch_textasset` 用 `errors="replace"` 解码重编码 → **非 UTF-8 字节被 U+FFFD 替换,内容永久损坏**(U+FFFD 重编码为 EF BF BD)。
- 窗口窄但存在;写回侧无严格校验。

**发现 F4(代码路径确认,P1):typetree 写回对无内嵌类型树(typeless)文件的依赖**

- IL2CPP 游戏常剥离类型树;UnityPy 对未知 MonoBehaviour 用模板树。`save_typetree` 序列化结果可能与 Unity 实际解析不一致,重开验证只能验证「我们自己写的字节没变」,不能验证「Unity 能解析」。对 typeless 文件应优先 rawstr 字节级补丁。

**发现 F5(设计缺口,P2):非 Addressables bundle 的 CRC 引用无覆盖**

- 游戏非 catalog.bin 方式传递 CRC(如配置表里手写 bundle CRC)时,只改 bundle 不改调用方 → CRC Mismatch → 资源拒绝加载。无法通用修补,应在发布报告里警示。

**发现 F6(设计事实):闭环测试的盲区**

- `flow_closure_check.rule_translate` 保证译文 ≤ 原文且全中文片段 → 固定容量池写回永远走 pad 分支且验证用 startswith/片段找回 → **F1 在闭环测试中必然全绿**。真实翻译(服务)才触发。→ 修复后必须新增针对 F1 的专项验证。
