# 写回后“口口口口”字体问题专项审计与全面修复计划

日期：2026-08-13  
审计范围：Unity 游戏中文字已写回，但运行时显示为方框、空白或缺字  
审计对象：字体指纹、静态字体替换、BepInEx 字体回退、写回发布闸门、字体报告与测试  
工作边界：仅做只读审计并撰写方案；未修改实现代码、字体文件或游戏资源，未启动真实游戏

> **交给实施 Agent：** 实施时必须先使用 `brainstorming` 审批设计，再使用 `writing-plans` 拆分任务，按 `tdd` 或 `test-driven-development` 完成红—绿—重构；每个 Phase 结束前执行 `dev-issue-tracker` 自审、`verification-before-completion`、代码审查和分支收尾。不得把本报告视为跳过项目开发锁链的授权。

## 1. 执行摘要

“口口口口”通常不是翻译文本没有写进去，而是游戏拿到正确 Unicode 文本后，当前渲染字体找不到对应字形，最终显示 tofu 方框。当前工具已经拥有三类有价值的能力：

1. Legacy `Font` 内嵌字体数据替换；
2. 按 Unity 版本选择的 TMP 静态 SDF 字体包替换；
3. Mono 游戏使用 BepInEx 插件，为 TMP、uGUI、UI Toolkit 和 TextMesh 添加运行时中文回退。

问题不在于“完全没有字体功能”，而在于这些能力没有形成可证明完整的字体兼容闭环。当前最关键的错误口径是：

> 只要静态替换命中任意一个字体对象，项目层就把整个游戏标记为 `runtime_verified=True`；这只能证明“至少有一个对象被改写并能重开”，不能证明“所有承载中文的文本对象都有字体、材质和字形”。

与此同时：

- 静态替换会跳过动态 TMP 字体、布局不匹配、跨文件图集、找不到图集、未知 Unity 版本等对象；这些跳过目前主要是 warning，不改变已命中的全局 PASS。
- TMP 静态验证只核对载荷复制、字形表数量与图集字节，没有拿“本次实际译文字符集”逐字符验证。
- 运行时插件只用一个代表汉字验证字体工厂和健康状态，不能证明数千个中文、全角标点、扩展字、符号和 emoji 都能显示。
- `font-health.json` 统计扫描/应用次数，但没有记录“哪些中文文本对象被看见、需要哪些字符、缺哪些字符、是否真正请求过每个字形”。
- IL2CPP 没有运行时 fallback provider；只要部分静态替换命中，就可能把未覆盖的动态/自定义字体栈藏在 PASS 后面。
- NGUI、BMFont、Sprite/位图字体以及游戏自定义文字渲染器没有纳入统一消费者清单。指纹层虽能识别部分 NGUI/位图证据，但主写回闭环没有为它们给出可靠的自动注入与发布语义。

因此，本报告的最终判断是：

> 当前字体层是“多种补救器的集合”，还不是“以实际译文字符集和实际字体消费者为中心的覆盖证明系统”。大量方框字与现有 `runtime_verified` 报告并不矛盾，因为现有验证对象和用户看到的最终渲染对象不是同一个层级。

## 2. 证据等级与诊断边界

### 2.1 证据等级

- **已证实**：当前源码调用链可以直接证明条件、跳过、状态赋值或验证缺失。
- **高概率**：代码结构足以造成方框，但具体游戏是否命中需要读取该游戏资产或运行时证据。
- **待实机确认**：只有实际启动特定游戏、进入具体场景后才能确认的渲染、材质、动态加载和第三方 UI 行为。

### 2.2 “口口口口”必须先分类

实施阶段不得看到方框就直接替换字体。应先区分：

| 症状 | 常见含义 | 判别方法 | 本计划归属 |
|---|---|---|---|
| 每个汉字显示同样的空心方框 | 字体缺字形/tofu | 写回文件中的 Unicode 正确；换支持 CJK 的字体后恢复 | 字体覆盖主问题 |
| 文本本身已被写成 `□□□□` 或 `口口口口` | 上游文本已丢失 | 重开资产后读到的就是方框码点 | 编码/翻译/写回数据问题，不得归因字体 |
| `ä¸­æ–‡` 一类字符 | UTF-8 被错误按其他编码解码 | 对比原始字节与解码链 | 编码问题 |
| 中文完全空白 | 字形、材质、shader、alpha 或 mesh 刷新失败 | 字体含字符但无顶点/材质不可用 | 字体资产链问题 |
| 只有少数字为方框 | 字体覆盖不完整或 fallback 未命中 | 逐码点核对字符表/`HasCharacter` | 字符集覆盖问题 |
| 只在某些菜单、场景或 DLC 出现 | 不同字体对象/动态加载/Addressables | 按场景和消费者 ID 对照 | 覆盖范围问题 |
| 图标变方框或消失 | `<sprite>`、私用区、图标字体被中文字体替换 | 核对富文本标签、PUA 和原图标字体 | 不应粗暴全替换 |

### 2.3 本次没有做的事情

- 没有真实启动用户遇到问题的游戏，因此不能断言某一个具体字体资产就是唯一根因。
- 没有修改字体或重新打 AssetBundle。
- 没有用截图 OCR 猜测方框位置。
- 没有把静态重开成功当作运行时渲染成功。

## 3. 当前字体处理真实调用链

```text
FontConfig（默认启用 Source Han Sans SC）
  → Project.write_all
     → 文本/二进制译文写回
     → install_static_fonts
        ├─ 扫描部分 Unity 容器
        ├─ Legacy Font：替换内嵌 TTF + 修正度量
        └─ TMP_FontAsset：按 Unity 主版本选静态 SDF bundle
             ├─ 布局匹配才替换
             ├─ 静态且未覆盖 CJK 才替换
             ├─ 同文件 atlas 才支持
             └─ 重开验证字形数量与 atlas 字节
     → 若 static.replaced > 0
        ├─ 整个项目直接标记 runtime_verified=True
        └─ Mono 再尝试部署 BepInEx 插件；失败只 warning
     → 若 static.replaced == 0
        ├─ Mono：部署 BepInEx 运行时 fallback，当前只到 payload_deployed
        └─ IL2CPP：provider unsupported，通常以 WARN 发布
     → 重开写回文件
     → 四态闸门
     → 发布输出副本
```

Mono 运行时插件的路径是：

```text
BepInEx Awake
  → 加载 font.ttf 与翻译表
  → 创建 Legacy dynamic Font
  → 反射创建动态 TMP_FontAsset
  → 挂全局和逐 TMP_FontAsset fallback
  → 每 2 秒扫描 TMP / UI.Text / UI Toolkit / TextMesh
  → 替换字体或补 fallback
  → 用一个代表汉字写 font-health.json
```

上述路径各自有局部验证，但缺少一个把“本次译文所需字符 → 字体消费者 → 字体资产/fallback → 实际覆盖结果”贯穿起来的深层模块。

## 4. 已确认的 P0 问题

### P0-1 全局字体 PASS 由“任意对象命中”触发

**证据**

- `hanhua/core/unity/font_replace.py:35-43` 的 `FontReplaceResult` 只有总 `replaced`、`skipped`、`warnings` 和文件路径，没有发现数、消费者数、逐栈覆盖率或未覆盖对象。
- `hanhua/core/project.py:1425-1445` 只要 `static.replaced` 为真，就构造 `FontInstallResult(... runtime_verified=True, provider_id="static_font_replace")`。
- `hanhua/core/project.py:1258-1268` 随后把 `font.runtime_verified` 直接映射为运行时闸门 PASS。

**影响**

一个游戏可以有 30 个字体资产，其中 1 个成功替换、29 个动态或不受支持；报告仍显示 `runtime_verified`。用户在命中未覆盖字体的场景看到大量方框时，工具却认为字体层已通过。

**解决方案**

废除“静态命中数大于零等于运行时验证成功”的语义。静态结果必须至少包含：

- `consumers_discovered`
- `font_assets_discovered`
- `assets_patched`
- `assets_already_covered`
- `assets_runtime_covered`
- `assets_unsupported`
- `required_codepoints`
- `covered_codepoints`
- `missing_codepoints`
- `unresolved_consumers`
- `evidence_level`

只有所有承载可发布中文的消费者都能映射到完整覆盖的字体链时，静态字体门才可 PASS。

### P0-2 验证没有使用本次实际译文字符集

**证据**

- `hanhua/core/unity/font_replace.py:581-630` 的 TMP 重开验证核对字形数量、图集尺寸/格式和图集字节等于预置载荷，但不核对每个实际译文字码点是否在字符表中。
- `font_plugin/Hanhua.FontFallback/HanhuaFontPlugin.cs:1096-1109` 从翻译中找到第一个 CJK 字符作为代表字；找不到则使用“汉”。
- `font_plugin/Hanhua.FontFallback/HanhuaFontPlugin.cs:1028-1053` 只把这个代表字的布尔结果写入各 adapter 健康信息。
- Unity 6000 字体包 manifest 明确只有 6448 glyph，低于其他包的 3.3–3.8 万，实际译文包含扩展字、符号或特殊标点时更容易产生局部缺字。

**影响**

“汉”能显示不能证明“龘、〇、㈠、→、★、全角标点、组合字符或游戏所需图标”能显示。大量译文中任意少量缺字也可能造成界面出现成片方框。

**解决方案**

建立 `RequiredGlyphSet`：从最终可发布译文、运行时翻译表和工具主动添加的截断符号中生成 Unicode scalar 集合，并保留来源定位。验证必须以该集合为输入，而不是常用汉字样本或单代表字。

字符集规则：

1. 只纳入最终 approved/publishable 译文。
2. 解析 TMP/Rich Text，标签名和属性语法不作为字形；实际显示的标签内容保留。
3. `<sprite>` 不转换成普通 Unicode 字符；图标资产单独验证。
4. 保留中文标点、全角字符、数学/方向符号、货币符号、拉丁字符和实际 emoji。
5. 以 Unicode scalar value 处理非 BMP 字符，禁止用单个 UTF-16 `char` 截断代理对。
6. 每个码点记录至少一个 `entry locator`，便于报告告诉实施者哪个译文引入缺字。

### P0-3 静态替换的跳过对象不会推翻全局成功

**证据**

- `hanhua/core/unity/font_replace.py:536-564` 会跳过 TMP 布局不匹配、动态/空字体、已判定覆盖 CJK、找不到 atlas 或 atlas 替换失败的对象。
- `hanhua/core/unity/font_replace.py:473-474` 不支持跨文件 atlas 引用。
- `hanhua/core/unity/font_replace.py:695-709` bundle 解析和单资产失败只记录 warning 后继续。
- `hanhua/core/project.py:1422-1425` 把这些问题收集为 warning；只要另一个对象替换成功，仍进入静态成功分支。

**影响**

最可能显示方框的对象恰好是被跳过的对象，但报告的主状态被其他成功对象覆盖。

**解决方案**

跳过项必须结构化，不能只是字符串。每条记录包含：

```text
consumer_id / asset_path / serialized_file / path_id / stack
font_asset_id / atlas_id / material_id
reason_code / severity / runtime_fallback_possible
required_codepoints / missing_codepoints
```

对于绑定了可发布中文的消费者：

- 可由已验证运行时 fallback 覆盖 → `DEFERRED_TO_RUNTIME`；
- 没有可靠 runtime provider → `BLOCKED_FONT_COVERAGE`；
- 未证明该对象承载中文 → `UNRESOLVED`，默认至少 WARN，严格发布模式 BLOCKED。

### P0-4 IL2CPP 缺少运行时兜底，却允许不完整静态结果发布

**证据**

- `hanhua/core/font_support.py:611-625` 明确 IL2CPP provider 未经验证，仅允许静态写回。
- `hanhua/core/project.py:1486-1497` 在静态无命中时返回 unsupported。
- `hanhua/core/project.py:1265-1266` provider unsupported 映射为 WARN，而非字体发布阻断。
- 当 IL2CPP 有任意静态命中时，又会落入 P0-1 的全局 `runtime_verified=True`。

**影响**

IL2CPP 游戏的动态 TMP、Addressables 后加载字体或自定义渲染器没有第二道保险。对这类游戏，未覆盖对象放行后几乎必然要靠人工碰运气发现方框。

**解决方案**

IL2CPP 使用严格字体覆盖策略：

- 所有已知中文消费者静态覆盖完整 → PASS；
- 存在未知/动态消费者但没有 runtime provider → BLOCKED，除非用户明确选择“生成候选输出，不标记可发布”；
- `allow_partial` 不能顺带绕过字体 BLOCKED；文本部分发布和字体不完整必须是两个独立授权。

### P0-5 `runtime_verified` 名称与证据含义不一致

**证据**

- 静态字体替换从未运行游戏，却被标记为 `runtime_verified=True`。
- Mono 插件刚部署时返回 `payload_deployed=True, runtime_verified=False`；健康文件只有下一次重新扫描/解析输出目录时才可能被读取。
- `font-health.json` 即使存在，也只证明某次进程中至少一个适配器和一个代表字可用，不证明全部场景和全部译文。

**影响**

报告、UI 和历史记录把三种不同证据混为一谈：文件载荷已部署、静态资产可重开、真实游戏渲染已覆盖。维护者因此难以正确理解风险。

**解决方案**

改成不可混淆的证据等级：

1. `NOT_ANALYZED`
2. `PAYLOAD_PREPARED`
3. `STATIC_ASSETS_VERIFIED`
4. `STATIC_COVERAGE_VERIFIED`
5. `RUNTIME_ADAPTER_STARTED`
6. `RUNTIME_GLYPH_COVERAGE_VERIFIED`
7. `SCENE_RENDER_ATTESTED`

禁止将 3 直接命名成 6。发布策略依据“覆盖是否完整”，显示层另行展示证据深度。

### P0-6 运行时健康协议无法证明“看见并覆盖所有中文消费者”

**证据**

- `font-health.json` 只记录 adapter 状态、单 glyph 布尔值、累计应用数和翻译匹配数。
- 运行时插件扫描 `Resources.FindObjectsOfTypeAll`，但没有输出发现总数、带中文文本总数、逐对象字体链、缺字列表或异常对象身份。
- 只要某类应用计数大于零且相应 adapter 的代表字可用，`read_font_health` 就可能认为其可用。

**影响**

扫描到 1 个 TMP 对象并添加 fallback，不代表另外 100 个 TMP 对象都成功；应用次数也不能证明对象最终实际使用该 fallback 渲染了全部字符。

**解决方案**

升级健康协议为 `font-attestation.json`，最少记录：

- run/session ID、游戏版本、插件版本、Unity/TMP 版本；
- 每类消费者的 discovered / chinese_text / covered / missing / failed 数；
- RequiredGlyphSet 的 SHA-256 与数量；
- 每个 adapter 的逐码点 `HasCharacter`/动态添加结果；
- 缺字码点及其文本定位/对象 ID；
- 动态字体工厂、shader、atlas、fallback 绑定和 mesh refresh 的结果；
- 场景覆盖列表与最近更新时间；
- capped 的失败对象明细及完整失败计数。

约束：`covered + missing + failed == chinese_text_consumers`，并验证健康文件对应当前发布版本和当前 RequiredGlyphSet，防止读取上一次运行的陈旧 PASS。

## 5. P1 问题

### P1-1 字体消费者发现不完整

当前指纹会识别 TMP、uGUI、NGUI 和 `.fnt`，但主字体替换/插件主要覆盖 Legacy Font、TMP、UI.Text、UI Toolkit 和 TextMesh。以下路径没有统一闭环：

- NGUI `UILabel` / `UIFont`；
- BMFont `.fnt` + atlas；
- SpriteFont/自定义纹理字库；
- 自定义 mesh 文本渲染器；
- 原生插件/视频字幕/网页 UI；
- Addressables 或远端包中延迟加载的字体；
- 多 player/嵌套 Unity player 的各自字体资产。

方案：增加 `FontConsumerInventory`，先识别渲染栈和消费者，再决定 provider；无法识别的渲染栈不得被一个通用 Font 替换成功掩盖。

### P1-2 资产候选扫描范围与排除规则过粗

`_asset_candidates` 依靠扩展名/名称和目录遍历寻找容器，可能遗漏无常规后缀的自定义 bundle、StreamingAssets 包、运行时下载资源或嵌套包。排除规则以 path part 方式表达时也难以证明与真实路径语义一致。

方案：复用统一扫描清单和 Unity 容器识别结果，不再独立 `rglob` 猜测。字体分析输入应来自扫描阶段已经验证的容器 catalog，记录每个未解析容器。

### P1-3 TMP “已覆盖 CJK”判定不是本次译文覆盖判定

`_tmp_covers_cjk` 使用常用汉字样本和 CJK 数量门槛。一个字体即便覆盖 2000 常用字，也可能缺少本游戏译文中的具体字；反之，一个只覆盖本游戏所需 500 字的子集字体可能完全够用，却会被无谓替换。

方案：判定改为 `required_codepoints ⊆ effective_font_chain_codepoints`。保留常用汉字样本只能作为提示性质量信息，不能做发布门。

### P1-4 静态 TMP 只支持同文件 atlas

跨 SerializedFile/AssetBundle 的图集引用直接返回不支持，这在复杂 bundle/Addressables 游戏中会造成系统性漏覆盖。

方案：建立全局 `AssetReferenceResolver`，以 source container + fileID/pathID + dependency table 定位 atlas/material；实施前先用真实 fixture 固化跨文件引用。不允许通过改 PathID/GUID 的方式“简化”问题。

### P1-5 TMP 字体资产、图集、材质和 fallback 链的验证不完整

当前重点验证字体表与 atlas 像素，但不同 TMP 版本还涉及 material、shader、atlas texture list、fallback table、population mode、source font、特殊字符表和 mesh 刷新。载荷字段部分复制成功仍可能出现空白、花屏、材质异常或缓存旧字形。

方案：定义按 TMP 代际版本化的 `TmpFontContract`，每个 bundle manifest 声明并验证必要字段。验证包含引用可解析、材质 shader 可用、atlas/character/glyph 索引一致、特殊字符可用、fallback 无循环。

### P1-6 运行时插件用 UTF-16 `char` 表达探测字

代表字和 `HasCharacter` 路径以单个 `char` 为中心，无法正确表达非 BMP Unicode scalar，例如部分 emoji 和扩展汉字。即使主要问题是 BMP 中文，这也会让“全部字符覆盖”升级时产生结构障碍。

方案：协议和 RequiredGlyphSet 使用 Unicode scalar (`uint32`)；TMP 走支持 `uint`/string 的 API，Legacy 无法覆盖的 scalar 明确报告，不做截断探测。

### P1-7 运行时插件的失败策略是局部 fail-open

每个扫描类别异常后记录日志并继续，游戏不会崩溃是对的，但工具没有在下一次读取 attestation 时把失败升级为发布/验收失败。插件运行故障因此可能只留在 BepInEx 日志里。

方案：运行时稳定性与发布安全分离：游戏继续运行，但 attestation 标记 adapter/consumer FAILED；工具导入后不得显示字体已通过。

### P1-8 配置只有启用和字体文件名，无法表达策略

`FontConfig` 只有 `enabled` 与 `filename`。无法表达严格/候选发布、允许哪些渲染栈、静态优先还是 runtime 优先、特殊字符策略、是否保留游戏自带 CJK 字体、最大 atlas 等。

方案：新增有效字体策略，但保持默认简单：

```text
mode = strict
static_policy = prefer_existing_then_patch
runtime_policy = required_for_dynamic_mono
unknown_consumer_policy = block
glyph_scope = published_translations
preserve_icon_fonts = true
```

高级设置不必暴露在首屏；报告必须记录最终策略快照。

### P1-9 UI 对真实字体状态表达不足

UI 的字体标签主要识别旧的 `runtime_fallback/disabled/unavailable`，而当前后端已经产生 `runtime_verified/payload_deployed/unsupported` 等值，存在显示语义漂移。成功 toast 也可能在字体 warning 存在时只告诉用户“写回已验证”。

方案：UI 只消费强类型 `FontCoverageOutcome`；显示“静态覆盖 18/22、运行时待验证 4、缺字 7、未知消费者 1”，不要只显示一个抽象等级。

### P1-10 没有把方框症状回流为结构化问题

当前历史记录大量写 `runtime_verified`，但没有统一的 `font_missing_glyph` 实例、截图位置、场景、消费者、缺字码点、字体资产和最终解法。问题难以跨游戏复用。

方案：为字体问题建立结构化案例：

```text
game/version/runtime/scene
symptom_kind
entry_locator/text
consumer_stack/consumer_id
font_asset/material/atlas
missing_codepoints
static_outcome/runtime_outcome
resolution/provider_version
```

## 6. P2 问题

### P2-1 字体包 manifest 缺少可机器验证的字符覆盖摘要

当前 manifest 有 glyph 数、Unity 版本和 hash，但没有字符集 hash、Unicode ranges、明确缺失码点、TMP package 版本、材质/shader 契约。6448 glyph 的 Unity 6000 包只写“覆盖常用汉字”，不足以对具体游戏做决策。

### P2-2 warning 是自由文本，无法形成门禁和统计

`dynamic font (0 glyphs)`、`atlas not found`、layout mismatch 等都是字符串。调用方只能展示，无法可靠按原因、消费者和严重度聚合。

### P2-3 历史报告把文件级验证和渲染级验证混写

“重开验证 True”“字体 runtime_verified”“总体 PASS”经常并列出现，但缺少证据定义。应在新报告中显示验证层级和未验证范围，避免继续积累不可比较的数据。

## 7. 推荐目标架构

```text
Final Publishable Translations
             │
             ▼
RequiredGlyphSet
  - Unicode scalars
  - source locators
  - markup/icon separation
             │
             ▼
FontConsumerInventory
  - TMP / Legacy / uGUI / UI Toolkit / TextMesh
  - NGUI / BMFont / Sprite / Custom / Unknown
  - consumer → font → material → atlas references
             │
             ▼
FontCompatibilityPlanner
  ├─ ExistingFontCoverage
  ├─ StaticFontPatchProvider
  ├─ MonoRuntimeFallbackProvider
  ├─ BitmapFontProvider
  └─ Unsupported/Manual Provider
             │
             ▼
FontCoverageVerifier
  - per consumer
  - per codepoint
  - per asset contract
             │
             ▼
FontPublishGate
  ├─ PASS: all required consumers covered
  ├─ PENDING_RUNTIME_ATTESTATION
  ├─ CANDIDATE_ONLY
  └─ BLOCKED
             │
             ▼
Runtime Font Attestation（适用时）
```

### 7.1 `RequiredGlyphSet`

这是整个方案的事实源。字体是否足够，不应再问“是否大致支持中文”，而应问“是否覆盖本次要显示的所有 Unicode scalar”。建议输出：

```json
{
  "schema": 1,
  "translation_snapshot": "sha256:...",
  "codepoints": [32, 33, 20013, 25991],
  "sources": {
    "20013": ["asset#resources.assets#123/m_Text"]
  },
  "excluded_markup": ["sprite", "color", "link"]
}
```

### 7.2 `FontConsumerInventory`

消费者而不是字体文件才是覆盖单位。一个字体资产存在，不代表某个文本组件使用它。Inventory 至少要回答：

- 这是什么渲染栈？
- 它会显示哪些已写回/运行时翻译条目？
- 当前绑定哪个字体、fallback、材质和 atlas？
- 资产是静态、动态、Addressables 还是未知来源？
- 哪个 provider 能覆盖它？

无法把静态条目精确绑定消费者时，可用保守策略：该场景/容器内所有文本消费者都要求覆盖整个 RequiredGlyphSet；后续有证据再缩小。

### 7.3 `FontCoverageOutcome`

不要继续用多个松散布尔字段。建议领域终态：

```text
COMPLETE_STATIC
COMPLETE_RUNTIME_ATTESTED
PENDING_RUNTIME_ATTESTATION
INCOMPLETE_KNOWN
UNRESOLVED_CONSUMERS
UNSUPPORTED_STACK
ERROR
```

`COMPLETE_*` 才能标记正式可发布。`PENDING_RUNTIME_ATTESTATION` 可以生成候选副本并允许用户启动测试，但 UI 不得称“字体验证通过”。

### 7.4 静态覆盖与运行时证明的职责

- 静态验证证明：文件结构、引用和所需码点在预期字体链中完整。
- 运行时 attestation 证明：插件实际加载、看见目标消费者、字体工厂工作、所需码点可生成/可查询。
- 截图/场景回归证明：最终视觉没有方框、空白、材质错误和布局灾难。

三个层次不能互相冒充。

## 8. 发布门设计

### 8.1 门禁输入

- 最终可发布译文快照；
- RequiredGlyphSet；
- FontConsumerInventory；
- provider 计划；
- 静态 patch/验证结果；
- 适用时的当前版本 runtime attestation；
- 用户是否只生成测试候选，而非正式发布。

### 8.2 决策表

| 状态 | 正式发布 | 测试候选 | UI 文案 |
|---|---:|---:|---|
| 所有消费者静态完整覆盖 | 允许 | 允许 | 字体静态覆盖完整 |
| Mono 动态消费者，runtime attestation 完整 | 允许 | 允许 | 字体运行时覆盖已证明 |
| 已部署 runtime，但尚未运行验证 | 禁止称正式完成 | 允许 | 等待启动游戏完成字体验证 |
| 已知缺字/未覆盖消费者 | 禁止 | 允许（红色警告） | 缺字 N 个、未覆盖对象 M 个 |
| 未知渲染栈 | 严格模式禁止 | 允许 | 发现未支持字体栈 |
| IL2CPP 动态消费者且无 provider | 禁止 | 允许 | 当前无法自动保证动态字体 |
| 仅文本编码重开成功 | 与字体门无关 | 与字体门无关 | 文本写回通过，字体尚未验证 |

### 8.3 `allow_partial` 的边界

现有“允许部分写入”不能默认绕过字体门。应拆成：

- `allow_partial_text_writeback`
- `allow_unverified_font_candidate`

第二项只允许生成测试候选，不允许报告为正式验证完成。

## 10. 必需测试矩阵

| 测试 | 必须证明 |
|---|---|
| 文本重开为正确中文，但字体缺字 | 归类 `font_missing_glyph` |
| 文本重开已是方框码点 | 归类 data/writeback corruption |
| 1 个静态字体成功 + 1 个 dynamic 跳过 | 全局 INCOMPLETE/BLOCKED |
| 字体含 3000 汉字但缺本次一个字 | 精确报告缺失码点和 locator |
| 字体只含本次 500 字 | 可判完整，不按 2000 字门槛误替换 |
| unknown Unity version | 不静默跳过 TMP 后继续 PASS |
| TMP layout mismatch | 消费者失败进入门禁 |
| 同文件 atlas | 字形、atlas、material 契约通过 |
| 跨文件 atlas | resolver 成功或明确 BLOCKED |
| 动态 TMP + Mono | runtime pending → attested |
| 动态 TMP + IL2CPP | 无 provider 时正式发布阻断 |
| 代表字成功、实际另一字失败 | runtime attestation 失败 |

## 11. 可观测性与报告格式

每次写回报告至少输出：

- 翻译快照 hash、RequiredGlyphSet hash、字符总数；
- 汉字、标点、符号、非 BMP、PUA 分类数量；
- 每种渲染栈的消费者发现数；
- 字体资产总数、已覆盖、已替换、runtime pending、未知和失败数；
- 每个 provider 的选择原因与证据等级；
- 缺字 Top-N：`U+XXXX 字符 → locator → consumer/font`；
- 跳过/失败 reason code 分布；
- 静态 coverage 终态；
- runtime attestation 的版本、session、场景、时间和 snapshot 匹配状态；
- 正式发布资格与测试候选资格分开显示。

推荐摘要示例：

```text
字体覆盖：BLOCKED
所需字符：2,431（CJK 1,876 / 标点 71 / 其他 484）
消费者：TMP 28 / uGUI 4 / BMFont 1
完整覆盖：30 / 33
待运行验证：2
不支持：1（BMFont atlas injection）
缺字：3（U+9F98、U+20BB7、U+2605）
正式发布：否
测试候选：是
```

## 12. 验收指标

### 12.1 确定性指标

- 所有 publishable 译文 Unicode scalar 都进入 RequiredGlyphSet。
- 所有已知中文消费者都有且只有一个 coverage 终态。
- `covered + runtime_pending + unsupported + failed + unresolved == discovered`。
- 正式发布时 `missing_codepoints == 0`。
- 正式发布时 `unsupported == failed == unresolved == 0`。
- runtime attestation 必须与当前 translation snapshot 和 glyph-set hash 一致。

### 12.2 实机指标

- 基准场景中可见中文方框/空白为 0。
- BepInEx/TMP 日志无 missing glyph、atlas/material/fallback 异常。
- 场景切换和动态加载后 coverage 不下降。
- 字体处理不造成启动崩溃、Addressables CRC 错误或材质丢失。
- 关键 UI 无因字体度量引起的不可操作布局问题；此项属于相邻布局验收，不替代字形覆盖。

### 12.3 性能指标

- 静态字体 inventory/coverage 可缓存，翻译未变时不重复全库解析。
- 运行时逐字验证按 font asset + glyph hash 缓存。
- 周期扫描无持续内存增长，不在每 2 秒重复创建字体/atlas。
- 大字符集验证耗时和内存有上限并写报告；不得为了性能退回单代表字。

## 13. 紧急止血方案

完整架构实施前，建议先完成以下最小安全修正，但不能把它们称为最终解决：

1. 立即取消 `static.replaced > 0 → runtime_verified=True`。
2. 静态结果存在任何 dynamic/layout/atlas 跳过时，字体门至少 WARN；IL2CPP 严格模式 BLOCKED。
3. 报告把 `runtime_verified` 改成 `static_assets_reopened`，避免误导。
4. 从本次译文生成字符集，至少核对预置 TMP bundle 的 character table 是否完整覆盖。
5. Unity 6000 字体包若缺本次任何码点，立即 BLOCKED，不以“常用汉字”放行。
6. Mono runtime payload 只显示“已部署，待启动游戏验证”，不显示字体通过。
7. 把所有字体 skipped/warnings 完整导出，UI 显示数量与最高严重度。

这些止血措施会增加 WARN/BLOCKED 数量，但能立即停止“报告 PASS、游戏方框”的错误承诺。

## 14. 不推荐的修法

1. 不要简单把 Source Han Sans 替换成更大的字体后宣布修复；消费者可能根本没有使用它。
2. 不要只增加常用汉字样本；必须核对本次真实译文字符集。
3. 不要把所有 TMP 字体强制替换；图标字体、sprite/PUA 和游戏自带 CJK 字体会被破坏。
4. 不要只看 `glyph_count`；character、glyph、atlas、material 和引用必须一致。
5. 不要只把 warning 改成 BLOCKED 而不建立消费者清单，否则无法解释和修复。
6. 不要把 BepInEx 文件成功复制等价为插件成功加载。
7. 不要用一个“汉”字的 `HasCharacter` 结果证明整个游戏字体健康。
8. 不要让“允许部分写入”隐式绕过字体门。
9. 不要用截图 OCR 作为唯一自动门；它适合最终视觉抽查，不替代资产/码点证明。
10. 不要在未知 TMP/Unity 版本上猜 bundle；应 fail closed 并生成明确兼容任务。

## 15. 推荐执行顺序

最高优先级不是先扩充字体包，而是修复验证语义：

1. **Phase 0**：用 fixture 锁定“部分命中却全局 PASS”。
2. **Phase 1**：RequiredGlyphSet + FontConsumerInventory。
3. **Phase 2**：静态逐消费者、逐码点 coverage。
4. **Phase 4 的发布门部分**：先停止错误 PASS。
5. **Phase 3**：运行时全字符 attestation。
6. **Phase 4 完整编排/UI/headless 统一**。
7. **Phase 5**：NGUI/BMFont/自定义字体栈。
8. **Phase 6**：版本矩阵与真实游戏场景验收。

建议将“停止假 PASS”和“扩大字体支持面”分开：先让工具诚实地说不知道或未覆盖，再逐个增加 provider。这样不会继续用错误成功状态掩盖真实方框问题。

## 16. 最终结论

当前工具已经解决了若干真实字体难题，包括 Legacy TTF 替换、TMP 版本化载荷、atlas 内嵌、Mono 动态 fallback 和健康文件。但这些能力的成功单位仍然是“某个模块做过某件事”，而用户关心的成功单位是“每一条可见中文在每一个实际文本组件里都有可渲染字形”。两者之间缺少覆盖证明，所以大量“口口口口”仍可能发生。

本专项最核心的修复不是再加一个字体，而是引入三个事实源和一个发布门：

- `RequiredGlyphSet`：到底要显示哪些字符；
- `FontConsumerInventory`：到底由哪些组件和字体显示；
- `FontCoverageOutcome`：每个消费者到底覆盖、待验证还是失败；
- `FontPublishGate`：不完整覆盖不得冒充正式完成。

完成这条闭环后，工具才可以从“尽量注入中文字体”升级为“可证明本次汉化没有字体方框风险”；对暂时不支持的 NGUI、位图字体、IL2CPP 动态字体或自定义渲染器，也能给出准确的阻断原因和下一步，而不是继续输出一个误导性的 `runtime_verified`。
