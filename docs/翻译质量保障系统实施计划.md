# 翻译质量保障系统实施计划（详细版）

> 依据：《游戏汉化工具翻译质量保障系统》技术方案（2026-08-13，用户提供）
> 目标：把「翻译 + 知识 + 语境 + 检索 + 审核 + 修正 + 记忆」七环节闭环从方案落地为代码
> 对照基线：当前代码 v0.25.x（地毯式排查第九轮收官）
> 本文档中的函数/模块名以当前代码为准；标注「新增」的文件/表为规划产物

---

## 一、背景与目标

游戏汉化的难点不是「能不能翻译」，而是**在正确的游戏语境下，把原文准确、稳定、一致地翻译成中文**。当前系统的硬规则质量门已能拦截结构破坏（占位符/标签/键名），但存在一个明确的形态边界：**语义错译**——译文形态完整（占位符、换行、数字全对）但语义错（实证：PRESS→「媒体」）。这类错误无法用确定性规则拦截。

因此目标不是「换更强模型」，而是**「让不同组件处理不同类型的问题」**：

| 组件 | 职责 | 现状 |
|---|---|---|
| Hy-MT2-1.8B | 翻译（不负责最终判定） | ✅ 已接入 |
| 硬规则质量门 | 结构安全（程序优先于 AI） | ✅ 20+ 检查 |
| 术语库 | 术语一致性 | ✅ glossary.db + AgentMemory |
| 特殊文本库 | 六类文本的翻译规则 | ✅ 六库 text 域 |
| 翻译记忆 | 避免重复翻译、保持一致 | ✅ ProjectStore.memory + AgentMemory |
| **Qwen3.5-4B 深度审核** | 语义审查 + 四级分级 | ✗ 待接入 |
| **风险分流** | 决定哪些文本需要深审 | ✗ 待实现 |
| **Qwen3-Reranker-0.6B** | 候选语境匹配排序 | ✗ 待接入 |
| **Qwen3-Embedding-0.6B** | 知识检索/相似召回 | ✗ 待接入 |
| **游戏语境库** | 多义词消歧的结构化依据 | ✗ 待建设 |
| 自动重译 | 修复已发现的问题 | ✅ 已有（原因标签驱动） |
| 知识沉淀 | 证据驱动积累 | ✅ AgentMemory + 六库 learn |

最终闭环：**检索 → 翻译 → 检查 → 筛选 → 深审 → 修正 → 记忆**。

## 二、目标架构

```
游戏原文（含上下文：场景/UI位置/前后文/文本类型）
      │
      ▼
知识检索层（阶段 4 起：Qwen3-Embedding-0.6B 向量检索；之前：启发式精确/子串命中）
  术语库 glossary.db / 游戏语境库 context_entries(新) / 特殊文本库 knowledge.db(text域)
  翻译记忆 project.memory / 经验记忆 agent_memory.db / 错误案例库 knowledge.db(fail_case)
      │
      ▼
Hy-MT2-1.8B 主翻译（BatchTranslator，含记忆直填与上下文注入）
      │
      ▼
硬规则质量门（validate_translation_quality，20+ 确定性检查）
      │
      ▼
风险分流（新增）：质量门通过 + 低风险 → 直放 ｜ 可疑 → 深审
      │
      ▼
Qwen3.5-4B 深度审核（阶段 1 起）：PASS / MINOR / MAJOR / CRITICAL + 审核理由
   ├─ PASS      → 写库（进翻译记忆/AgentMemory 候选）
   ├─ MINOR     → 记录，放行
   ├─ MAJOR     → 修正（审核理由注入重译 prompt）→ 再审核
   └─ CRITICAL  → 重译 → 再审 → 仍失败则降级处理（保留原文/标记）
      │
      ▼
知识沉淀（术语库 + 语境库 + 翻译记忆 + 错误案例库）
```

**双模式**：
- **轻量模式**（默认）：1.8B + 四库 + 硬规则 + Reranker-0.6B——只对可疑文本调 4B 深审
- **高质量模式**：追加 Embedding + 向量库 + 全量 4B 深审 + 自动重译 + 二次审核 + 知识沉淀

## 四、总体设计

### 4.1 审核四级定义

| 级别 | 定义 | 处置 |
|---|---|---|
| **PASS** | 语义/结构/术语全部正确，可直接写库 | 写库 + 进记忆候选 |
| **MINOR** | 语义正确但有小瑕疵（语序不自然、用词不够地道）；不改变含义 | 记录到审核日志，放行 |
| **MAJOR** | 语义有偏差（术语误用、语气不符、信息缺失但未颠倒）；译文需修正 | 修正后再审；不直接写库 |
| **CRITICAL** | 语义错误（否定颠倒、人物关系颠倒、数量/时间错误、含义完全不同）；译文不可用 | 重译；重译仍失败则保留原文标记 blocked |

审核维度（对应方案 §8 清单）：语义一致性 / 否定 / 人物关系 / 条件与因果 / 数量 / 时间 / 语气 / 信息完整性 / 术语一致性 / 风格。

### 4.2 风险分流决策表

深审成本是硬约束（实测目标 <15% 条目），分流规则（任一命中即送审）：

| 信号 | 来源 | 判定 |
|---|---|---|
| 质量门失败 | `QualityResult.reasons` | 已走重试链且最终失败 → 送审（判定 MAJOR/CRITICAL 或放行） |
| 术语冲突 | `GlossaryStore.detect_conflicts` / 词对命中但译文未用术语 | 送审 |
| 多义词 | 词表命中（Resume/Save/Charge/…）且语境库无记录 | 送审 |
| 长句 | 原文 tokens > 60 | 送审 |
| 否定/条件/比较词 | 原文含 not/no/never/if/unless/more/than/only 等 | 送审 |
| 角色关键文本 | dialogue 域、含专名 | 送审 |
| 其余 | — | 直放 |

### 4.3 新增数据结构（规划）

**游戏语境库表**（新库 `context.db` 或 knowledge.db 新域，阶段 2）：

```sql
CREATE TABLE context_entries (
    id INTEGER PRIMARY KEY,
    source_text TEXT NOT NULL,        -- 原文
    fingerprint TEXT NOT NULL,        -- 语境指纹（游戏+场景+UI位置+文本类型+相邻文本摘要）
    correct_meaning TEXT,             -- 该语境下的正确词义（如 Resume=继续）
    recommended_translation TEXT,     -- 推荐译文
    confidence REAL DEFAULT 0.5,      -- 0~1，证据驱动
    source TEXT,                      -- 'manual' | 'review_confirm' | 'memory_promote'
    game TEXT,                        -- 来源游戏
    scene TEXT, UI_POSITION TEXT, text_type TEXT,
    context_window TEXT,              -- 相邻文本（前 2/后 2）
    evidence_count INTEGER DEFAULT 1,
    created_at TEXT, updated_at TEXT
);
CREATE UNIQUE INDEX idx_ctx_fp ON context_entries(source_text, fingerprint);
```

**错误案例库升级**（knowledge.db fail_case 表补字段，阶段 5）：

```sql
ALTER TABLE fail_case ADD COLUMN wrong_translation TEXT;
ALTER TABLE fail_case ADD COLUMN correct_translation TEXT;
ALTER TABLE fail_case ADD COLUMN error_type TEXT;      -- 语义/否定/关系/术语/结构/数量/时间/语气
ALTER TABLE fail_case ADD COLUMN review_reason TEXT;
```

**向量索引表**（新库 `vector.db` 或独立文件，阶段 4）：

```sql
CREATE TABLE vectors (
    id INTEGER PRIMARY KEY,
    obj_type TEXT NOT NULL,           -- term | context | memory | source_text | fail_case
    obj_id INTEGER NOT NULL,          -- 原表主键
    text TEXT NOT NULL,
    embedding BLOB NOT NULL,          -- fp32 序列化
    game TEXT, created_at TEXT
);
CREATE INDEX idx_vec_type ON vectors(obj_type);
```

### 4.4 模型服务层（阶段 0 建立）

当前只有翻译模型一个 llama.cpp 服务。新增审核/重排模型需要统一接入层：

```
hanhua/core/model_registry.py（新增）
  ModelSpec: name / path / kind(translate|review|rerank|embed) / backend(cpu|gpu) / gpu_layers / ctx / keep_alive / max_concurrency / budget
  ├─ translate: Hy-MT2-1.8B（现有）
  ├─ review:    Qwen3.5-4B（阶段 1 起）
  ├─ rerank:    Qwen3-Reranker-0.6B（阶段 3 起，固定 CPU）
  └─ embed:     Qwen3-Embedding-0.6B（阶段 4 起，固定 CPU）
```

运行方式：llama.cpp server 双实例（翻译 8080 / 审核 8081），Reranker/Embedding 可共用审核实例或随阶段独立。预算与超时沿用 `ReviewConfig` 已验证配置。

**硬件智能分配**（阶段 0 起，`hanhua/core/hardware_planner.py` 新增）：

- **0.6B×2（rerank/embed）固定 CPU**：任务毫秒~秒级（批量嵌入、top-100 重排各一次前向），占 GPU 无收益
- **4B 审核 / 1.8B 翻译按用户硬件自动分配**，决策表（显存为 GPU 可用显存）：

  | 可用显存 | 4B 审核 | 1.8B 翻译 |
  |---|---|---|
  | 无 GPU | CPU（降速可用） | CPU |
  | 4~6GB | GPU（唯一名额，keep-alive 按需加载） | CPU |
  | 6~8GB | GPU 常驻 | GPU 按需加载（翻译批次换入） |
  | ≥8GB | GPU 常驻 | GPU 常驻 |

- 决策依据：`vram.py` 显存预估（权重 + KV + 计算缓冲）≤ 可用显存 90% 才上 GPU；GPU 加载失败自动回退 CPU（复用 `local_model.py` 现有 cuda_missing 回退链）
- 常驻/按需用 llama.cpp `--keep-alive`（闲置自动卸载）实现，不做手动杀进程
- KV 控制随分配联动：显存紧张时 4B 降 `--ctx-size` 4096 / `--parallel` 1（审核单条逐条审，不需并行槽）

### 阶段 1：深度审核 + 四级分级（P0，~3 周）

**目标**：质量门之后增加「风险分流 → 4B 深审 → 分级处置 → 反馈式重译」闭环，堵住语义错译边界。

**涉及模块**：reviewer.py（扩展）、batch_translator.py（重译反馈）、quality.py（分流信号）、memory.py/agent_memory.py（记忆门禁联动）、新 `scripts/` 审核报告。

**任务**：

| # | 任务 | 细节 |
|---|---|---|
| T1-1 | 审核 prompt 四级化 | 审核 prompt 要求输出 JSON：`{level: PASS|MINOR|MAJOR|CRITICAL, reason, issues:[{type, detail, suggestion}]}`；审核维度按 §4.1 九项；输出解析复用 `_parse_verdict` 模式（reviewer.py:157） |
| T1-2 | `ReviewResult` 扩展 | 新增 `level` 字段；`needs_optimization` 保持兼容（level in (MAJOR, CRITICAL)）；新增 `apply_verdict(entry)` 分发：PASS→写库、MINOR→记录放行、MAJOR→修正队列、CRITICAL→重译队列 |
| T1-3 | 风险分流器 | 新增 `risk_gate.py`：按 §4.2 决策表筛可疑条目；输出 `{entry, signals, priority}`；质量门失败但重试链已耗尽的条目强制送审 |
| T1-4 | 反馈式重译 | `BatchTranslator._chat_each` 重译路径支持注入「审核理由」：prompt 追加 `[审核反馈] 上次译文：X；问题：{reason}。请针对问题修正`；复用 `_record_failure_attempt` 预算（CRITICAL 重译计入 attempt，与现有失败链共享预算防死循环） |
| T1-5 | 再审收敛 | MAJOR/CRITICAL 修正后过质量门 + 再审一次；仍 CRITICAL → 保留原文 + 标记 blocked + 写错误案例；不无限循环（上限 2 轮） |
| T1-6 | 记忆门禁联动 | 深审 MAJOR/CRITICAL 的译文不进 `add_memory`/AgentMemory 候选；PASS 译文优先进记忆；修正后译文进记忆候选 |
| T1-7 | 审核日志 | 新增 `review_report.md`（每游戏）：送审数/各级分布/重译收敛率/CRITICAL 明细（原文/错译/审核理由/正确译文） |
| T1-8 | 测试 | `tests/test_review_levels.py`：四级判定解析、分流决策表全分支、反馈重译注入、记忆门禁（MAJOR 不进记忆）、收敛上限（2 轮停） |

**验收**：
- 抽查 200 条历史译文：CRITICAL 级错译（否定/关系颠倒/语义完全错误）检出率 100%，MAJOR+CRITICAL 检出率 ≥95%
- 正常译文 4B 调用率 <15%
- 重译后 MAJOR/CRITICAL 收敛率 ≥80%（两条：或通过、或降级处理）
- 1900+ 现有测试全绿（不回归）

### 阶段 3：Reranker-0.6B 语境匹配（P1，~2 周）

**目标**：候选语境排序——「哪些候选真正符合当前语境」，解决启发式命中噪声（跨游戏「相似指纹」可能语义不同）。

**涉及模块**：model_registry.py（rerank 注册）、新 `rerank_gate.py`、batch_translator.py（注入改造）。

**任务**：

| # | 任务 | 细节 |
|---|---|---|
| T3-1 | Reranker 服务接入 | 0.6B 成本低可全量；批量接口 `rerank(query_text, candidates) -> [(candidate, score)]` |
| T3-2 | 候选生成 | 启发式候选（精确/子串/同 object 同 role/词对命中）上限 20 条 → Reranker 排序 |
| T3-3 | Top-K 注入 | 只注入 score ≥ 阈值 的 Top-3 候选到 prompt（注入量封顶，不随库增长） |
| T3-4 | 存疑标记 | Reranker 高分但质量门失败 → 该词对/语境标记存疑（`context_entries.suspicious` 或 AgentMemory 拒绝计数），防污染 |
| T3-5 | 测试 | `tests/test_rerank_gate.py`：排序正确性（Resume 样本选「继续」最高分）、Top-3 封顶、存疑标记 |

**验收**：Resume 类样本 Reranker 最高分为正确译文；prompt 注入量不增（Top-3 封顶实测）；吞吐 ≥ 20 条/秒（本地 0.6B）。

## 六、测试与验证策略

- **每阶段新增测试与现有 1900+ 全绿**是硬门槛，否则阶段不验收
- **回归基线**：9 轮排查沉淀的 6 款代表游戏（各文本来源类型）重跑，译文差异 diff 审查（预期：语义错译减少、正常译文不变）
- **验证方式**：沿用现行流程——扫描→翻译→写回→重开比对，不实机、不用云端审核
- **假数据保护**：Reranker/深审的判定不得作为「正确性依据」写死规则，只作为证据；规则与词对变更一律过测试

## 七、优先级与资源

| 优先级 | 阶段 | 理由 |
|---|---|---|
| P0 | 阶段 1 深度审核四级分级 | 质量保障核心闭环；语义错译（PRESS→媒体）是当前唯一能力边界 |
| P0 | 阶段 2 游戏语境库 | 多义词是方案全文核心痛点；与阶段 1 共用上下文采集 |
| P1 | 阶段 3 Reranker | 初版流程要求；0.6B 成本低 |
| P1 | 阶段 4 Embedding | 完整版核心；去重收益直接 |
| P2 | 阶段 5 自动学习 | 依赖前四阶段数据积累 |

**模型预算**（本地 GGUF，llama.cpp）：
- Qwen3.5-4B Q4_K_M ~3GB：审核，只跑可疑批次；GPU/CPU 按硬件智能分配（§4.4）
- Hy-MT2-1.8B Q6_K ~1.5GB：翻译；GPU/CPU 按硬件智能分配（§4.4）
- Qwen3-Reranker-0.6B Q8_0 ~0.7GB：语境排序，可全量；固定 CPU
- Qwen3-Embedding-0.6B Q8_0 ~0.7GB：检索，阶段 4 加；固定 CPU
- 全量 GPU 常驻 ≈9GB（12GB 卡）；串联/按需峰值 ≈4GB（6GB 卡可跑）；0.6B×2 不计 GPU

## 八、风险与边界

1. **审核成本**：4B 全量不可接受——§4.2 分流 <15% 调用率是硬约束；若实测超限，先加启发式信号再放宽
2. **审核模型自身误判**：4B 也可能错——审核结果过质量门复查；MINOR 不拦（防过度修正）；审核误判案例进错误案例库
3. **重译死循环**：收敛上限 2 轮 + attempt 预算共享（T1-5）；仍失败保留原文 + blocked 标记（与现有跳过语义一致）
4. **语境指纹可靠性**：场景归属依赖提取器证据——采集失败降级无语境（T2-1），不阻塞
5. **本地部署约束**：0.6B~4B 级别，符合方案「尽量用 0.6B~4B 解决绝大部分任务」，不用大模型
6. **流程约束**：现行免实测/免云端审核指令不冲突——4B 审核为本地模型；云端语义审核维持停用
7. **硬件差异**：分发用户显卡从无到 12GB 不等——由 §4.4 智能分配决策表兜底（T0-5）；无 GPU/4GB 以下降级全 CPU 模式，审核吞吐慢但可用；低档硬件在验收时冒烟覆盖
