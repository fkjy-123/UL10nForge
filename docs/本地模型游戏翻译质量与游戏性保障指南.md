# 本地模型游戏翻译质量与游戏性保障指南

> 研究日期：2026-08-08  
> 适用范围：Unity 游戏文本提取、机器翻译、本地 GGUF/llama.cpp 模型、质量审校、写回和运行时显示  
> 目标：把“模型输出了一段中文”提升为“语义正确、角色一致、格式安全、可玩且可回归的游戏译文”。

## 1. 这份文档解决什么问题

游戏翻译不是普通句子翻译。一个游戏文本条目可能同时包含：

- 玩家要理解的自然语言；
- 不应翻译的 key、ID、资源地址、输入绑定或脚本命令；
- `{0}`、`{name}`、`%s`、Smart String、Ink/Yarn/Fungus 变量；
- TMP/HTML/Rich Text 标签、图标、链接和颜色；
- 角色、地点、阵营、技能、物品、任务等需要跨数万条保持一致的专名；
- 受界面宽度、语音时长、按钮尺寸和字体字数约束的显示文本；
- 需要根据说话人、上下文、性别、复数、时间和剧情状态变化的译文。

因此，翻译模块的正确目标不是最大化“已翻译条数”，而是最大化以下函数：

```text
可理解性 × 语境正确性 × 术语一致性 × 格式安全 × 游戏性安全 × 可审计性
```

任何一项为零，都可能导致玩家看到乱码、错误剧情、无效按键、任务卡死或游戏崩溃。

## 2. 翻译质量的完整维度

### 2.1 语言质量

| 维度 | 需要回答的问题 | 典型失败 |
|---|---|---|
| 忠实度 | 是否保留原意、条件、因果和语气 | 否定词丢失、技能效果被反转 |
| 流畅度 | 中文是否自然，是否像游戏文本 | 逐词翻译、英文语序、机器腔 |
| 术语一致 | 同一概念是否总用同一译法 | 同一技能在菜单和对白中有多个名字 |
| 角色声音 | 是否符合角色身份、年龄、阵营和情绪 | 小孩说成公告，反派说成客服 |
| 篇章连贯 | 前后句、任务链和剧情因果是否连贯 | “他/她/它”、时态、指代错乱 |
| 文化适配 | 双关、俚语、笑话、宗教和禁忌是否合适 | 直译后笑点消失或冒犯玩家 |
| 地域规范 | 简体中文、标点、数字、日期和单位是否统一 | 中英文标点混用、单位误换算 |
| 可读性 | 短按钮、长说明、字幕是否易读 | 按钮太长、字幕超时、信息拥挤 |

### 2.2 工程质量

| 维度 | 保护对象 |
|---|---|
| 结构 | JSON/XML/CSV/SQLite/Unity 序列化格式 |
| 变量 | 占位符、复数、性别、选择器、脚本变量 |
| 标记 | TMP、HTML、Markdown、BBCode、引擎标签 |
| 输入 | `[E]`、`Enter`、手柄 glyph、Control Path |
| 标识符 | key、GUID、资源名、Action、事件、地址 |
| 编码 | UTF-8/16、BOM、EOL、Unicode normalization |
| 长度 | 固定容量、按钮宽度、字幕时长、语音时长 |
| 可追溯 | 原文、译文、来源、上下文、模型、版本、审校状态 |

### 2.3 游戏性质量

游戏性翻译的最低要求：玩家能完成操作、理解反馈、完成任务并在异常情况下恢复。需要特别验证：

- 操作提示和真实绑定一致；
- 任务目标、完成条件和失败条件没有被改义；
- 技能、装备、属性、数值、单位和状态没有翻转；
- 物品名、描述、图标和效果对应；
- 菜单按钮的语义和实际行为一致；
- 角色说话人、头像、语音和字幕不串位；
- 系统错误、警告、存档提示仍然能指导玩家恢复；
- 不因中文变长导致按钮、对话选择或拖拽区域无法使用。

## 3. 翻译模块应采用的端到端架构

```text
扫描候选
  → 角色/来源分类
  → 结构保护与占位符抽取
  → 上下文组装
  → 术语/风格规则注入
  → 本地模型翻译
  → 格式解析与质量门
  → 记忆/一致性检查
  → 人工审校分流
  → 写回或运行时映射
  → 游戏性回归
  → 失败记录和术语反哺
```

翻译模块不应直接接受“裸字符串并返回裸字符串”。中间表示至少需要：

```json
{
  "id": "stable-locator",
  "source": "Press {key} to open",
  "source_language": "en",
  "target_language": "zh-CN",
  "role": "interaction_prompt",
  "source_kind": "runtime_tmp",
  "scene": "House",
  "speaker": "Mara",
  "context_before": [],
  "context_after": [],
  "protected_spans": ["{key}"],
  "glossary_terms": [],
  "translation": "按 {key} 打开",
  "quality": {},
  "model": "local-model-name",
  "prompt_version": "v3",
  "status": "review"
}
```

## 4. 文本角色分类：模型必须知道自己在翻译什么

### 4.1 推荐角色

```text
menu_button
menu_label
tooltip
interaction_prompt
dialogue
narration
choice
quest_title
quest_objective
quest_condition
item_name
item_description
skill_name
skill_description
status_effect
tutorial
notification
system_error
save_message
achievement
loading_tip
subtitle
credit
developer_note
name_or_place
format_template
localization_key
engine_string
unknown_candidate
```

### 4.2 不同角色使用不同翻译策略

| 角色 | 翻译策略 |
|---|---|
| menu_button | 短、动作明确、优先常用 UI 译法 |
| interaction_prompt | 保留按键 token，动词统一，避免长句 |
| dialogue | 结合说话人、前后句和情绪，保持口语自然 |
| narration | 保持叙事时态、文风和段落节奏 |
| choice | 与后续分支结果语义一致，避免模棱两可 |
| quest_objective | 用可执行动词，目标和数量不能丢 |
| item_name/skill_name | 术语优先，名称长度稳定，避免随意意译 |
| item_description | 功能、数值、限制和条件优先于文采 |
| system_error | 明确说明原因和恢复动作，不追求文学化 |
| subtitle | 简短、易读、与语音时间匹配 |
| credit | 通常保留人名、公司、网址和法律文本 |
| format_template | 只翻译自然语言，严格保护变量和语法 |
| localization_key | 不翻译，仅建立映射 |

没有角色信息时，宁愿降低置信度并进入审校，也不要用同一个 prompt 翻译按钮、对白、技能说明和日志。

## 5. 上下文是本地模型质量的第一决定因素

### 5.1 只传一句话会导致什么

本地模型在缺少上下文时容易：

- 把 `Charge` 翻成“收费”而不是“蓄力/冲锋”；
- 把 `Back` 翻成“后面”而不是“返回”；
- 无法判断 `Light` 是光、轻、点亮还是轻攻击；
- 无法区分角色对玩家说话还是旁白；
- 把技能说明翻成自然句，丢掉数值和条件；
- 把同一专名按普通词翻译；
- 把 UI 键名、资源名或错误码当成可译文本。

### 5.2 推荐上下文优先级

```text
字段角色/组件类型
  > 当前对象和场景
  > 同一对话/任务/表格相邻条目
  > 说话人、头像、阵营、性别
  > 术语表和已确认记忆
  > 前后句和剧情摘要
  > 全局游戏设定档
```

上下文应分层发送，避免把整部游戏塞进 prompt：

1. 固定系统规则：目标语言、输出格式、保护要求；
2. 游戏设定：时代、世界观、译风、禁译项；
3. 角色卡：说话人、身份、语气、称谓；
4. 术语片段：只注入当前文本命中的术语；
5. 邻近语料：同一对象/任务/对话的少量已确认译文；
6. 当前条目或小批次。

### 5.3 上下文窗口管理

本地模型的 context 不只是输入文本，还包含 system prompt、术语、示例、历史消息和输出。上下文过长会导致：

- 后半段被截断；
- 模型忘记前面的结构规则；
- 翻译批次互相串台；
- KV cache 占用显存，触发 OOM 或性能骤降；
- 长句回显原文或输出不完整 JSON。

建议：

- 先按 token 预算而非字符数分批；
- 结构规则放在稳定前缀，利用本地服务 prefix cache；
- 术语只发送命中项；
- 同一角色/表/任务分组，不把互不相关条目混批；
- 长文本先按语义句切分，再在质量门通过后合并；
- 为输出预留足够 completion budget；
- 发生截断时记录 context estimate、batch ID 和原文，不要把半截译文写回。

## 6. 本地部署模型的推理策略

### 6.1 模型选择

选型不能只看通用 benchmark。应在目标游戏样本上比较：

- 英中/日中/韩中等真实语言方向；
- UI 短词、对白、技能说明、字幕、幽默和脏话；
- 占位符、TMP 标签、输入 token 保留率；
- 长文本、批量 JSON、低资源专名；
- 术语表服从率和角色口吻；
- 速度、显存、上下文长度和失败恢复成本。

建立小型固定评测集：每个角色至少 20 条，每个文本角色至少 50 条，包含已知难例、历史失败和边界格式。换模型或量化版本必须重新跑此集合。

### 6.2 采样参数

本地翻译通常优先稳定和可重复：

- UI、术语、结构化模板：低 temperature 或近似贪心；
- 普通对白：适度 temperature，避免机械但保持语义；
- 创意台词：单独配置，不得影响系统提示和数值文本；
- `top_p/top_k/repeat_penalty` 需要成组记录；
- 失败重试时不要盲目提高随机性，应先缩短批次、加强结构保护或切换 fallback prompt。

每条结果记录模型名、GGUF/量化 hash、采样参数、上下文长度、prompt 版本和服务版本，确保可以复现。

### 6.3 批量与并发

批量提高吞吐，但会降低上下文隔离和单条失败定位能力。推荐：

| 场景 | 批量策略 |
|---|---|
| 菜单短词 | 同角色、同界面小批量 |
| 技能/物品 | 同一系统、相近字段和相同术语批量 |
| 对白 | 按场景/说话人/连续对话分批 |
| 超长剧情 | 句段切分，保留段落 ID 和邻接关系 |
| Smart String | 单条或极小批量，强结构校验 |
| 失败重试 | 降为单条，使用短 timeout 和 fallback |

并发槽位受 KV cache 和显存约束。并发过高会让本地服务排队、OOM、后半段变慢并增加重复请求。吞吐优化不能牺牲可恢复性。

### 6.4 本地服务故障处理

需要区分：

- 连接失败：服务未启动、端口错误；
- 429/队列满：节流并退避；
- 500/503/504：短暂服务错误，有限重试；
- 502/OOM：优先降并发、缩短 context 或重启服务；
- 非法 JSON：解析失败，先 fallback 单条，再进入人工队列；
- 模型回显：不是成功结果，必须通过 target-language/semantic 检测；
- 超时：保留未完成条目，不写入空译文。

重试必须幂等：同一稳定 ID 不能因为重试产生重复或覆盖人工译文。

## 7. Prompt 设计：让模型执行翻译而不是自由写作

### 7.1 固定系统规则

系统 prompt 应短、稳定、可版本化，至少声明：

```text
你是游戏本地化翻译器，不是解释器或聊天助手。
目标语言：简体中文。
只输出译文，不输出说明、前缀、引号、Markdown 或分析。
保留所有占位符、输入 token、富文本标签、变量、换行和专名标记。
不翻译 key、ID、路径、代码、URL、格式控制符和资源名。
遵守术语表、角色卡和当前文本角色。
```

### 7.2 按角色使用 prompt 片段

- `menu_button`：要求短、动词明确、使用已确认 UI 术语；
- `dialogue`：给说话人、情绪、前后句，要求自然口语；
- `quest_objective`：保护数量、目标、条件和动作顺序；
- `item_description`：优先功能和数值，统一术语；
- `subtitle`：控制长度和阅读速度，不添加解释；
- `format_template`：把保护槽位作为不可变 token；
- `system_error`：保留错误原因、恢复动作和技术标识。

### 7.3 少量示例比长篇规则更有效

示例应覆盖当前角色和失败模式：

```text
原文：Press {key} to open
译文：按 {key} 打开

原文：<color=#ff0>Charge</color>
译文：<color=#ff0>蓄力</color>

原文：You found %d coins.
译文：你找到了 %d 枚硬币。
```

示例中的标签、占位符、输入 token 必须与真实格式一致。不要给模型一个带错误保护的示例。

## 8. 术语、记忆和风格系统

### 8.1 术语表不是简单替换表

每个术语至少应有：

```text
source_term
approved_translation
category：角色/地点/技能/物品/系统/阵营
part_of_speech
case_sensitive
forbidden_translations
pronunciation_or_reading
note
scope：全局/游戏/场景/角色
status：候选/确认/废弃
```

同一英文词在不同角色可能有不同译法，术语表需要范围和优先级，而不是全局硬替换。

### 8.2 术语提取和审核

建议从以下位置自动发现候选：

- 重复出现的 Title Case/大写专名；
- Localization key 与 value 的对应关系；
- 任务、技能、物品、角色数据库；
- 同一 source 的多个译文不一致；
- 模型输出中的专名变体；
- 玩家/审校手动纠正记录。

候选术语不能直接强制写入。经过人工确认后进入 approved glossary，并反向修订已有译文。

### 8.3 翻译记忆

记忆条目应保存 source、target、角色、场景、说话人、版本、审校状态和 locator。匹配策略按优先级：

1. 完全相同且同角色/同项目；
2. 完全相同但不同场景；
3. 高相似句段；
4. 仅作为模型参考，不自动覆盖人工译文。

不要把历史机器译文无条件当作正确答案。记忆库必须区分 machine、reviewed、locked 和 rejected。

### 8.4 游戏风格指南

每个项目应明确：

- 简体中文或繁体中文规范；
- 现代、古风、科幻、恐怖、轻小说等整体文风；
- 角色称谓、敬语、性别和人称；
- 数字、单位、日期、货币和标点；
- 技能/物品命名规则；
- 粗口、敏感内容、宗教和文化表达；
- UI 短词和对白长句的不同偏好；
- 哪些品牌、作品名、专有名词保持原文。

## 9. 结构保护：先保护，再翻译，再还原

### 9.1 保护槽位

在送入模型前，把不可翻译片段替换成模型不易改写的槽位，例如：

```text
Press {key} to open
→ Press ⟦PH_0⟧ to open
→ 按 ⟦PH_0⟧ 打开
→ 恢复为 按 {key} 打开
```

保护清单包括：

- 占位符和格式参数；
- TMP/HTML/Rich Text/BBCode 标签；
- 输入键、手柄 glyph、sprite 引用；
- URL、路径、GUID、hash、正则和代码；
- XML/JSON 结构中的实体和 CDATA；
- SmartFormat、Ink、Yarn、Fungus 命令；
- 专名中明确锁定的片段。

### 9.2 保护槽位的质量检查

翻译前和翻译后都要记录多重集合和顺序：

- 缺少槽位：阻断；
- 多出槽位：阻断；
- 顺序变化：按语法类型决定，格式参数通常阻断；
- 槽位内部被模型修改：阻断；
- 标签不成对：阻断；
- 还原后与源格式解析结果不同：阻断。

### 9.3 不要把所有英文都保护

过度保护会让模型只翻译少量连接词，产生半翻译。保护的是结构和确认专名，不是所有大写词或短英文。对无法判断的内容，保留原文并降级到人工，而不是猜测。

## 10. 分段、批处理和长文本

### 10.1 分段原则

优先级：

1. 保留段落和换行；
2. 按对白/句号/问号/感叹号切分；
3. 不在变量、标签、引号和括号内部切断；
4. 不把说话人前缀和台词分成失去关系的两条；
5. 对字幕同时考虑时间码和阅读速度；
6. 合并时恢复原始分隔符和空白。

### 10.2 长文本策略

- 长段先生成章节摘要或上下文卡，再句段翻译；
- 给每个片段稳定 segment ID；
- 用前一段末尾和后一段开头少量上下文处理代词；
- 先翻译，再做术语/角色一致性二审；
- 不能把模型回显的原文当成功；
- 超过 context budget 时自动缩小批次，不是盲目增加 max_tokens；
- 合并后重新做段落、占位符和标签检查。

### 10.3 批次隔离

同一批次只放语境相近内容：

- 同一个菜单；
- 同一个任务或物品系统；
- 同一角色连续对白；
- 同一张 Localization 表且字段结构一致。

不要把日志、技能说明、对白、按钮和开发者注释放在同一批次。批量 JSON 输出必须有稳定 ID，任何缺 ID、重复 ID 或顺序异常都进入 fallback。

## 11. 本地模型的质量优化闭环

### 11.1 先建立目标游戏评测集

评测集必须来自真实游戏而不是通用英语句子，建议包括：

- 100 条 UI/按钮；
- 100 条对白，覆盖不同角色；
- 50 条任务和目标；
- 50 条技能/物品说明；
- 30 条字幕；
- 30 条占位符/富文本/输入提示；
- 30 条历史失败样本；
- 20 条故意超长和边界样本。

每个样本保存人工参考、术语要求、结构保护和质量标签。新模型、量化、prompt、参数或批次大小变化都必须跑回归集。

### 11.2 机器指标不能替代人工判断

BLEU、SacreBLEU、chrF、BERTScore、COMET 等可以用于比较模型或检测退化，但都有局限：

- 游戏短 UI 句子可能参考译文很多，BLEU 不代表可用性；
- 一句自然的中文可能与单一参考差异很大；
- COMET/BERTScore 可能忽略 key、输入 token、格式和游戏行为；
- 自动指标无法判断角色声音、按钮宽度和任务语义。

应同时统计：

```text
结构通过率
占位符通过率
输入 token 通过率
术语命中率
目标语言通过率
原文回显率
人工严重错误率
UI 溢出率
运行时原文残留率
```

### 11.3 严重度分级

| 级别 | 示例 | 处理 |
|---|---|---|
| S0 崩溃/安全 | 破坏文件、程序集或加载器 | 立即阻断并回滚 |
| S1 游戏不可玩 | 按键、场景、存档、任务无法继续 | 阻断发布 |
| S2 语义严重错误 | 技能数值/目标/否定关系错误 | 必须人工修正 |
| S3 结构/格式错误 | 占位符、标签、变量、乱码 | 自动拒绝写回 |
| S4 一致性错误 | 术语、称谓、角色声音漂移 | 进入批量修订 |
| S5 风格问题 | 生硬、标点、轻微措辞 | 可排队审校 |
| S6 偏好差异 | 不同但合理的表达 | 记录不强制阻断 |

### 11.4 失败样本驱动优化

每次失败必须记录原文、译文、上下文、模型、prompt、参数、错误类别和修正版。按错误聚类：

- 原文回显；
- 半翻译；
- 术语漂移；
- 专名误译；
- 否定/条件丢失；
- 数值和单位变化；
- 输入 token 丢失；
- 标签/占位符破坏；
- 长文本截断；
- JSON/数组输出失败；
- 角色口吻错误；
- 低质量中文或乱码。

每类错误分别改进规则、prompt、分段或模型，不要仅仅把所有失败样本塞回 prompt，避免上下文膨胀。

## 12. 质量门设计

### Gate A：输入合法性

- 原文非空且不是已确认 key/技术噪音；
- source/target language 已知；
- role/source_kind/locator 完整；
- 编码和格式已探测；
- 保护槽位解析成功。

### Gate B：模型输出合法性

- 非空；
- 没有解释、前缀、引号或 Markdown 包装；
- JSON 批次可解析，ID 集合与输入一致；
- 输出长度和 token 预算合理；
- 目标脚本符合预期；
- 没有明显原文回显或异常重复。

### Gate C：结构安全

- 占位符多重集合相等；
- TMP/HTML/BBCode 标签合法；
- 输入 token 顺序和语义保留；
- key、URL、路径、GUID、代码片段未改变；
- SmartFormat/剧情脚本语法仍可解析。

### Gate D：语言和语境

- 术语命中 approved glossary；
- 角色称谓和人称一致；
- 否定、条件、数量、时态和因果保留；
- UI/任务/技能使用合适的简洁度；
- 不包含模型幻觉、解释性补充或不存在的对象。

### Gate E：游戏性

- 操作提示与真实绑定匹配；
- 技能/物品数值和单位未改变；
- 任务目标与条件可执行；
- 菜单按钮语义与行为一致；
- 字体、布局、字幕时长和点击区域通过检查。

### Gate F：人工分流

自动通过：结构安全、低风险、术语明确、模型稳定。  
人工必审：对白关键剧情、双关、文化内容、S2 以上风险、长文本、低置信度、模型多次不一致和所有运行时新发现。

## 13. 游戏性翻译专项

### 13.1 任务和目标

任务文本必须保留：

- 动作动词；
- 目标对象；
- 数量和单位；
- 地点和条件；
- 时间限制；
- 完成/失败状态；
- 后续分支的因果关系。

“Find three keys”不能翻成“寻找钥匙”，因为数量是可玩条件。“Do not attack the guard”不能省略“不”。任务名可以文艺化，但目标描述必须可执行。

### 13.2 技能、物品和数值

优先保护事实：

- 伤害、治疗、倍率、持续时间、冷却；
- 物理/魔法/火焰等类型；
- 增益/减益、叠层、触发条件；
- 装备位置、稀有度、等级、消耗；
- 单位、百分号、正负号和小数精度。

翻译审校应把文本与实际数据表、技能实现或运行时 tooltip 对照，不能只看中文是否顺口。

### 13.3 对白、角色和剧情

角色卡建议包含：

```text
姓名、身份、年龄感、阵营、与玩家关系
常用称谓、人称、敬语等级、口头禅
情绪范围、幽默程度、禁用词、语言时代感
```

长对话要以场景和连续片段翻译，并用角色级记忆保持称谓。不能将所有对白独立翻译后再期待模型自动恢复关系。

### 13.4 选择项和分支

选择项必须与后续反应兼容：

- 选择项的语气要匹配角色反应；
- “Yes/No” 根据问题语义翻译，不固定成“是/否”；
- 选择短语中省略的主语不能被擅自补错；
- 分支 key、跳转标签和条件变量不能翻译；
- 关键分支至少进行一次实际游玩回归。

## 14. 中文本地化规范

### 14.1 标点和空格

项目应统一：

- 中文句号、问号、感叹号和省略号；
- 中英文混排空格策略；
- 数字与单位之间是否留空；
- 冒号、分号、括号和引号样式；
- 多行文本的换行位置；
- 省略号与字幕结尾节奏。

不要让模型自行决定每条文本的规范。将规则写入 style guide，并在质量门中检查。

### 14.2 简体中文与专名

- 人名、地名、组织名和作品名使用术语表；
- 不根据英文大小写擅自判断专名；
- 现实品牌、商标和开发者姓名遵守项目策略；
- 日文汉字、韩文专名和中文同形词需要语言方向判断；
- 繁简转换不能替代翻译，也不能破坏专名约定。

### 14.3 数字、单位、货币和日期

- 保留游戏真实数值；
- 明确是否本地化单位或只翻译单位名称；
- 百分号、小数点、千位分隔符一致；
- 时间格式与游戏逻辑、语音字幕保持一致；
- 货币名称和符号不要与程序内部 currency ID 混淆。

## 15. 特殊文本类型处理

### 15.1 UI 短文本

按钮、标签和提示应优先短、明确、可扫描。不要为了完整解释把按钮翻译成句子。对宽度受限文本保存：最大字符数、允许换行、自动缩放、组件类型和截图。

### 15.2 字幕

字幕质量同时受语言和时间约束：

- 保留时间码、说话人、样式和换行；
- 控制每秒阅读字符数；
- 与语音节奏、镜头和角色说话人对齐；
- 避免中文比原文更长导致读不完；
- 重要信息不能落在画面安全区外；
- 硬字幕必须另走 OCR/图片重制流程。

### 15.3 语音对白

有本地化语音时，译文长度、断句和口型可能受限制。没有配音时，字幕可以更完整，但仍需考虑音频时长。ASR 只能作为候选转录，必须人工校对专名和数值。

### 15.4 机翻不应处理的内容

默认跳过或人工处理：

- 纯 key/ID/路径/代码；
- 法律、许可证、开发者 credit；
- 玩家用户名、聊天和 UGC；
- 已经是目标语言且语义正常的文本；
- 乱码、base64、压缩/加密数据；
- 只含变量或技术标签的结构值；
- 不具备上下文且可能是专名的单词。

## 16. 人工审校与 LQA

### 16.1 审校不是逐条润色

人工优先处理高风险、高曝光和高影响文本：

1. 崩溃/输入/任务/存档相关；
2. 主菜单、设置、教程和核心循环；
3. 关键剧情、结局和角色建立；
4. 术语冲突和重复高频词；
5. OCR/运行时发现的原文残留；
6. 自动指标低或模型多次不一致的条目。

### 16.2 LQA 检查维度

- linguistic：语法、拼写、标点、自然度；
- terminology：术语、专名、称谓；
- functional：按钮、任务、数值、输入和流程；
- visual：截断、重叠、方框、换行、字幕阅读速度；
- cultural：敏感内容、双关、地域规范；
- audio：字幕、说话人、时间和配音一致；
- consistency：同一游戏系统跨页面一致。

每条 bug 要带重现步骤、截图/录屏、原文/译文、版本、严重度和建议修复，而不是只写“翻译不对”。

### 16.3 审校状态机

```text
pending
  → machine_translated
  → auto_checked
  → needs_review
  → reviewed
  → locked
  → written_back
  → runtime_verified
```

失败或拒绝状态必须可回到上一版，不得用空译文覆盖已审校译文。人工锁定条目不能被批量重译覆盖。

## 17. 记忆、缓存和可复现性

每次翻译记录：

- source hash 和 stable locator；
- 模型文件 hash、量化、推理后端版本；
- prompt/style/glossary 版本；
- temperature、top_p、top_k、repeat penalty；
- context size、batch size、并发和 fallback 次数；
- 输入/输出 token、耗时、错误和重试；
- 自动质量结果和人工修订。

缓存键必须包含目标语言、角色、术语/风格版本和结构保护版本。只用原文作为缓存键会把旧游戏风格、错误术语或其他语言方向的结果复用到新项目。

缓存应分层：

- 原始模型结果；
- 结构修复后结果；
- 自动通过结果；
- 人工审校结果；
- 运行时验证结果。

只有 reviewed/locked 结果才应作为高优先级翻译记忆。

## 18. 当前本地模型模块的针对性建议

现有项目已经具备：

- OpenAI 兼容本地服务和 llama-server 适配；
- 本地 context/batch/concurrency 配置；
- 批量翻译、单条 fallback、重试和进度回调；
- 术语表注入、内置 UI 参考译法；
- 占位符、标签、输入 token、目标脚本和原文回显检查；
- 长文本按换行/句子切分与结果合并；
- 翻译记忆、失败导出和质量状态。

建议下一轮按以下优先级加强：

### P0：防止错误译文进入写回

1. 以 role/source_kind 为输入强制选择 prompt，而不是所有条目共用一条指令；
2. 把 `input_token_mismatch`、`placeholder_mismatch`、`target_script_mismatch`、原文回显和 JSON ID 异常设为硬拒绝；
3. 质量门前后保存原始模型输出，禁止自动修复覆盖证据；
4. 空译文、解释性前缀、半翻译、非法标签不能进入写回；
5. 人工 locked/reviewed 条目禁止被自动批处理覆盖。

### P1：提高本地模型语境质量

1. 增加角色/场景/任务/对象级上下文卡；
2. 术语按当前条目命中注入，并支持禁用译法；
3. 对话按连续片段批处理，UI/技能/任务按系统分组；
4. 建立项目级 style guide 和角色卡；
5. 记录模型、prompt、量化、参数和 context budget，支持 A/B 回归。

### P2：提升一致性和人工效率

1. source/target/locator/context 多字段翻译记忆；
2. 术语候选挖掘、冲突检测和批量修订；
3. 相似句聚类和重复翻译合并；
4. 按 S0-S6 严重度排序审校队列；
5. 用 OCR/运行时差集把游戏内原文反馈到翻译审校。

### P3：模型与基础设施评测

1. 固定难例集比较模型和量化版本；
2. 统计吞吐、延迟、显存、OOM、回显率和重试率；
3. 对不同采样参数做可复现对照；
4. 让失败样本自动生成最小回归测试；
5. 用人工 LQA 结果校准自动评分，而不是盲信 BLEU/相似度。

## 19. 建议的每日翻译工作流

```text
读取游戏档案和术语表
  → 检查待翻译候选与角色分类
  → 先翻译高频 UI/术语/任务
  → 自动质量门
  → 审校高风险和低置信度
  → 更新术语和记忆
  → 翻译对白与长文本
  → 写回小批次 staging
  → 启动/输入/场景/存档回归
  → OCR 差集找残留
  → 处理失败记录并再次迭代
```

不要一开始就把全游戏所有候选一次性送入本地模型。先建立术语、UI 和核心流程基线，可以更早发现“翻译模块实际上改变了游戏行为”的问题。

## 22. 最终定义

本地模型翻译模块的“完成”不是所有条目都有中文，而是：

> 每条进入写回的译文都有明确角色、上下文、术语和结构保护记录；自动质量门没有发现硬错误；高风险内容经过人工或游戏内验证；翻译结果不会改变 key、输入、任务、数值、脚本和资源关系；模型和结果可复现，失败可追踪，输出可回滚。

本地模型可以承担高吞吐初译、候选生成、术语建议和一致性辅助，但不能独立承担最终的剧情、游戏性、格式和发布责任。游戏翻译质量来自模型、规则、记忆、人工 LQA 和运行时回归的联合系统。
