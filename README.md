# UL10nForge — Unity 游戏智能汉化工具

> 本地模型驱动的 Unity 游戏汉化工具：`扫描识别 → 批量翻译 → 质量检查 → 安全写回 → 经验积累` 全流程闭环，完全离线运行。与「原文丢给模型、翻完塞回去」不同，本项目以**质量保障为核心**——四模型分工 + 规则、记忆、知识库层层把关，翻译不是一次性输出，而是可验证、可积累的工程。

---

## 1. 引言：为什么需要「工程化汉化」

在开源工具的世界里，一份清晰的 README 是项目与用户之间的第一座桥。它向访问者展示项目的目标、功能和使用方法——这正是本文档的职责。

**路线说明**：社区主流方案（XUnity.AutoTranslator + MelonLoader）是**运行时注入**——游戏内 Hook 文本渲染函数实时替换译文，不改游戏文件；本工具走**静态写回**路线——把译文直接写进游戏文件（TextAsset/MonoBehaviour/本地化表/程序集），重开游戏即生效，无需 Mod 框架、无性能开销、卸载即原样。两者不冲突：本工具写回后，XUnity 类方案反而会拦截到中文原文（无额外收益），如需对照原文可保留原文件备份。

汉化不是「翻译一句话」这么简单，它是一道工程题：文本从哪来（识别）、哪些能改（分析）、怎么翻不坏（质量门）、怎么放回去（写回）、怎么越翻越准（积累）。本工具把每一步都做成**确定性检查 + 证据留档**，而不是依赖模型「碰运气」。

## 2. 项目描述与特色

### 2.1 一句话描述

**UL10nForge 是一个完全离线的 Unity 游戏汉化工作台**：识别 Unity 版本与文本存放方式，批量翻译游戏文本，经四级语义审核后按原格式安全写回，并把每次翻译的经验沉淀为可跨游戏复用的记忆与知识库。

### 2.2 特色与优势

| 方面 | 说明 |
|---|---|
| 可读性 | 四页工作台（项目卡 → 审校 → 翻译 → 设置），状态轨道直观展示每步进展 |
| 可接入性 | 零配置发行包：内置 Python 3.12 与 llama.cpp，解压双击即用 |
| 可维护性 | 核心层与界面解耦，全环节留档可审计，2562+ 测试护航 |

核心优势一览：

- **纯本地离线**：四模型随包运行，文本不上传任何服务器——无额度、无隐私顾虑、无网可用
- **四模型分工**：1.8B 翻译 + 4B 语义审核 + 0.6B 语境重排 + 0.6B 向量检索——翻译、把关、查证各有专用模型
- **规则护航**：模型负责翻译，规则负责「不翻坏」——每条译文过确定性质量门
- **深度审核闭环**：译文分 PASS/MINOR/MAJOR/CRITICAL 四级审查，错误带理由自动重译
- **全流程自动化**：检测 → 扫描 → 分析 → 翻译 → 审核 → 写回 → 重开验证，全环节留档可审计
- **越用越熟**：跨游戏经验记忆 + 术语库 + 语境库 + 六库知识库自动沉淀
- **安全写回**：只写回「质量通过 + 置信度合格」的译文，重开核对，不假报成功

## 3. 安装和使用说明

### 3.1 安装步骤

**发行包（零配置，推荐）**：

1. 解压发行包到纯英文路径（如 `D:\Games\111`——工具链对非 ASCII 路径支持有限）
2. 双击「启动UL10nForge.bat」
3. 首次启动自动拉起本地模型服务，就绪后进入工作台

**开发环境**：

```bash
pip install -r requirements.txt
python main.py
```

**硬件要求**：本地推理需 CUDA 显卡（8GB+ 显存推荐）或大内存纯 CPU 模式；模型档位按硬件自动规划（hardware_planner）。

### 3.2 快速开始（GUI 五步工作台）

| 步骤 | 操作 |
|---|---|
| ① | 拖入游戏文件夹，工具自动检测 Unity 版本与文本存放方式 |
| ② | 扫描全部可改文本（未知形态留档告警） |
| ③ | 设置页维护术语库（角色名/地名/物品名） |
| ④ | 翻译页一键批量翻译，审校页逐条确认 |
| ⑤ | 写回 → 「开始游戏」→ 重开核对 |

**命令行排查（免界面全流程 + 全环节记录）**：

```bash
python scripts/all_record_runner.py "<游戏目录>"
```

### 3.3 给新手的建议（社区经验 + 本项目实证）

1. **先挑简单的游戏练手**——视觉小说、2D 独立游戏文本量大但结构规整（本地化文件/TextAsset），成功率最高；3D 大作常加密/运行时拼接，门槛高
2. **游戏路径避免中文与特殊字符**——工具链（UnityPy/llama.cpp）与写回路径对非 ASCII 路径支持有限
3. **分章节汉化**——文字量大的游戏不必一次翻完：先跑一遍生成底稿，逐章游玩时在「文本审校」页精修、保存，下次翻译会直接复用已改内容（记忆直填）
4. **专有名词先沉淀**——在「设置」页维护术语库（角色名/地名/物品名），翻译会自动遵守；社区汉化组靠人工词典统一专名，本工具术语库自动注入并跨游戏复用
5. **看不懂状态就点开审校页**——「翻译失败」不等于坏：质量门拦截的是「可能翻坏」的译文，审校页可逐条看原因、手动改、重新翻译

## 4. 工作流程

| 步骤 | 做什么 |
|---|---|
| ① 检测 | 识别 Unity 版本与文本存放方式（Mono/IL2CPP/Addressables）；未知 runtime/版本显示 blocked，不假装成功 |
| ② 扫描 | 找出所有可改文本；未知形态告警留档（L1-L8 证据分层） |
| ③ 分析 | 判定哪些该翻、哪些不能碰——引擎配置/按键名/代码逻辑字符串翻错会坏游戏（有实证），词表对象、TMP 资产、输入绑定整体跳过 |
| ④ 翻译 | 记忆直填 → 语境重排选参考 → 模型翻译 → 质量门 → 四级语义审核 → 反馈重译 |
| ⑤ 写回 | 按原格式写回，重开比对逐条核对；四态闸门（文件/容器/对象/运行时）+ 原子发布 |

> 与社区离线三步法（提取 → 翻译 → 打包）对应：本工具的 ②③ = 提取（自动识别文本形态并归类），④ = 翻译（带质量门），⑤ = 打包（按原格式原子写回 + 验证）。差异在于每步都有确定性检查与证据留档，不是「提出来翻完塞回去」。
> 免费在线翻译源（百度/谷歌 API）质量参差且不可审计——本工具用本地模型 + 规则门 + 4B 审核替代，质量不依赖第三方服务。

## 5. 质量保障：三道关 + 审核环

每条译文过**三道关 + 审核环**：

1. **记忆关** —— 翻过的一模一样文本直接复用，前后一致（跨游戏共享，多游戏实证首轮直填）
2. **规则关** —— 20+ 确定性检查：占位符（`{player}`/`%s`）不丢、富文本标签不坏、**数字不误改**（"Deal 50 damage"→「造成 15 点伤害」判失败重译；50→五十 等价放行）、按键名保护（RMB→「右键」可以，译没了玩家找不到键）、半翻译拦截（"TOSS TRASH"→「TOSS 垃圾」重译）、对话脚本标记保护（`* ` 对话符/`^NN` 计时码，实证拦截 135 条）
3. **经验关** —— AgentMemory：只收质量门通过的译文，证据驱动晋升 active，被拒降级退休；术语库/语境库/六库知识库注入翻译上下文
4. **审核环** —— Qwen3.5-4B 五维审查（忠实/流畅/术语/占位符/风格）分四级，MAJOR/CRITICAL 带理由自动重译；词对沉淀入术语库（带语境保护，组合词对才可全局强制）

```python
from hanhua.core.batch_translator import BatchTranslator
from hanhua.core.translator import create_client
from hanhua.core.knowledge import KnowledgeBase

client = create_client(api)                     # 本地 llama-server 客户端

translator = BatchTranslator(
    client, batch_size=20, concurrency=1,
```

## 7. 支持范围（客观）

| 文本来源 | 提取 | 写回 |
|---|---|---|
| 本地化文件（JSON/CSV/TSV/XML/TXT/INI） | ✅ | ✅ 保留编码与换行 |
| TextAsset（含老 Unity 4.x/5.x） | ✅ | ✅ 可变长重建 + 重开验证 |
| MonoBehaviour 序列化字符串 | ✅ | ✅ 对象级重开验证 |
| Addressables（Unity Localization 表） | ✅ | ✅ Entry ID 写回 + CRC 同步 |
| Mono 程序集（C# #US 堆） | ✅ | ✅ 受原容量限制，超长截断并报告 |
| IL2CPP metadata | ✅ | ✅ 仅验证过 v24/27/29/31/39 |

**边界**：已处理样本覆盖多种 Unity 版本与打包方式，但**不等于所有 Unity 游戏通用**；不可汉化的（运行时拼接/加密/服务器下发/贴图文字/位图字体）明确阻断不假报；字体注入仅限 Windows x64 Mono，IL2CPP/x86 不保证中文显示。

### 字体（口口乱码）说明

社区方案（XUnity）遇到的口口乱码，本工具走**替换字体 + 完整性验证**链：写入游戏的字体需通过逐码点验证（所需字形 → 字符表 → 字形表 → 图集 → 回退链），缺失码点如实报告而非静默替换——防止「汉化了但全是口口」的假成功。支持粗细档位（FontConfig.weight）与运行时兜底（Mono 插件路径，仅 Windows x64）。

## 9. 当前局限（客观）

- **识别**：拼接/加密/服务器下发/贴图内文字无法识别（需 OCR）；未知形态可能漏识别（有告警留档，不保证全覆盖）
- **翻译质量**：1.8B 属小模型，复杂句/文学性表达质量有限；多义词易错（实证：PRESS→「媒体」、菜单语境 RESUME 误译）——4B 审核能拦语义错译，但误判率随文本量上升（实证 52%），需人工确认兜底
- **写回风险**：实证曾把引擎配置文件当普通文本翻译导致解析失败、引擎配置对象被翻导致输入失效——已修复但同类未知配置仍有风险；固定容量写回译文过长会截断
- **验证局限**：闭环验证到「重开比对」为止，不做实机测试（2026-08-12 指令）——UI 溢出、字体渲染等运行期问题可能漏检

## 10. 地毯式排查实证（0.26.x，多游戏收官）

0.26.x 系列对多款 Unity 游戏完成全流程闭环排查（涉及对话型 RPG 的 `* ` 对话脚本、增量式策略、恐怖/狩猎/旅馆等题材的独立游戏；按合规要求不列游戏名），每游戏三件文档（analysis/fix record/final report）见 `docs/all record/`。累计催生 30+ 修复（F1-F25+）：识别形态（IL2CPP v24-39/字面 `\n` 对话脚本/裸 `^NN` 计时码）、质量门（富文本/文件名段/方向词/占位符破碎/对话标记）、数据治理（方向词单字对污染源降级/C5 门禁拒绝单 token 词对）。

本轮实证数据（2026-08-13 终版）：对话型 RPG 收官战（18700 条目）催生 F13 对话标记三修，写回缺陷 208 条登记人工重译；收官战二（10031 条目）写回 9147 条仅 1 条缺陷（0.01%）、闸门 PASS、跨游戏记忆首轮直填 3 条、C5 门禁拒绝 `Load` 沉淀——质量门与记忆体系在收官战中全面生效。全量测试 **2562 passed**。

## 14. 未来计划

**近期（0.27.x）——核心功能聚焦**

1. **识别能力增强（最高优先）**
   - 更多文本形态覆盖：运行时拼接/动态文本（`il2cpp_display_template` 类）跟踪识别、Addressables 深层扫描补强
   - 贴图内文字 OCR 通道（本地 OCR 模型接入，覆盖贴图文字/位图字体）
   - 未知形态告警改进：L1-L8 证据分层→形态清单化，减少漏识别，skipped 率可量化
2. **写回可靠性（减少写回 bug）**
   - 引擎配置形态清单化保护（配置对象/配置文件全量登记，杜绝「翻坏引擎」类问题再发）
   - 固定容量写回截断改进（超长译文自动回退与上报，减少登记缺陷）
   - 重开验证覆盖面扩展（更多对象类型逐条核对）
3. **翻译质量**
   - 审校反馈重译链优化（MAJOR/CRITICAL 理由驱动的针对性重译，降低误判率）
   - 术语库/语境库注入增强（专名一致性跨游戏收敛）

**中期（0.28.x）**

- 多语言对支持（当前英→中，扩展日→中、韩→中；框架已预留 language pair 配置）
- 更大翻译模型档位（7B 级，适配 16GB 显存/大内存机器，按 hardware_planner 自动选择）
- 自动截图比对验证（替代实机测试：重开后截图关键界面，本地模型对比文本渲染）
- 翻译文件导入/导出（CSV/JSON），对接汉化组协作与人工校对工作流

**远期**

- GitHub 发布页 + 自动更新检查（含完整许可清单随包分发，届时确定本项目 LICENSE）
- 术语库/语境库社区共享通道（匿名化导出，防污染源治理保留）
- 插件化工具链（第三方提取/写回插件接口）
- 多平台（macOS/Linux 开发环境支持；写回与字体注入仍以 Windows 为第一目标）

> 计划按实证与用户反馈滚动调整；已完成的 13+1 项实施计划（2026-08-14）见 [docs/13项任务全面实施计划与检查计划-2026-08-14.md](docs/13项任务全面实施计划与检查计划-2026-08-14.md)。
